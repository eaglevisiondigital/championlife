# Preference callback replay binding — uninstalled source

A reproduced final-SQL defect returned `duplicate:true` when the same organization/event ID arrived with a different preference recipient or keyword. For example, after `STOP` for fictional recipient A, another `STOP` for B or `START` for A under that ID received a successful duplicate response although the requested preference was never applied. The existing delivery receipt checks already rejected conflicting replays; the preference ledger stored only keyword and could not prove an exact replay.

The forward migration `20261106071632_communications_preference_replay_binding.sql` adds nullable `receipt_binding` metadata to the existing `communication_keyword_events` table. It pins the accepted `comm_service` and external-lock function sources, validates existing service-only execution and private table/RLS boundaries, then replaces only the keyword receipt handling and the direct external-keyword lock acquisition. It preserves the function OID, owner, ACL, other service actions, existing preference reducer and audit. Historical migrations are unchanged. The file was generated with installed Supabase CLI 2.81.3; it has not been applied to a hosted database.

A new event binds its existing organization/event key to exact channel, keyword and provider, the SHA-256 of the canonical recipient, and a SHA-256 of the fixed current callback context. The existing H1 callback normalization and signature-verifier requirement remain unchanged. Direct calls through the existing privileged core service must also present a current exact SMS profile/control/environment context. They acquire the existing external-control lock before the organization lock, matching H1 order. The acceptance-sink path remains supported with its distinct organization/provider context and original recipient normalization.

No arbitrary callback JSON, raw recipient, body, secret or signature is added to the ledger. Digests are private comparison metadata, not anonymization, independent evidence or authorization. Required event ID/channel/keyword/address and any supplied provider are JSON strings; malformed values cannot become strings through SQL coercion. Extra or stale external context fails current-context comparison. The exact metadata projection has five fields: `channel`, `keyword`, `provider`, `recipient_sha256`, `context_sha256`.

An exact replay returns the existing duplicate response without another preference mutation or audit. A changed recipient, keyword, profile, provider or current source context raises an error, so the endpoint cannot acknowledge it as a successful duplicate. Existing historical events retain their original rows and NULL binding. They cannot be safely backfilled from a new proposal, so replay of an unbound historical event is held for separately reviewed reconciliation rather than acknowledged or applied again. This does not authorize deletion, new receipt IDs, resend or automatic retry.

The original preference semantics remain: STOP/UNSUBSCRIBE add only their existing suppression; a new START clears only STOP and grants no purpose or marketing consent; HELP grants no consent. Other suppression reasons, consent rows, outbox, attempts and UNKNOWN holds remain unchanged. New receipt, suppression and existing audit commit together; an audit failure rolls them all back. Organization/event uniqueness and existing serialization prevent concurrent duplicate or conflicting callbacks from recording two preferences.

## Validation and remaining gates

`node tools/communications-policy/preference-replay.native.mjs` uses disposable native PostgreSQL with fictional accounts, recipients and injected verifier output. It replays the exact accepted baseline plus the existing receipt/context/Resend chain before this migration. It covers the original failing assertion, source/ACL/RLS drift rollback, function identity preservation, legacy holds, exact and conflicting replays, current profile/context checks including direct service calls, strict input types, sink compatibility, tenant isolation, unchanged consent/outbox/attempts, audit rollback, separate-session duplicate/conflict races and a global-context change during a direct-service lock wait. Provider configuration and global sending remain disabled. These tests establish local source behavior, not real SMS signatures or provider acceptance.

Independent review and exact-head CI remain separate from genuine Auth/RLS/provider acceptance and approved target installation. No endpoint, verifier registry, account, key, role grant, sender, transport or provider is activated. Network Solutions and Auth SMTP remain unchanged. Release is NO-GO.

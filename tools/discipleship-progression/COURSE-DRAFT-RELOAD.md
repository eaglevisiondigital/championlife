# Device draft reload and deletion feedback — source only

The exact PR124 baseline reproduced two Lessons 1–4 defects: an explicitly saved blank answer was replaced with its older cloud answer on page reload, and a failed device-storage deletion cleared the displayed answers without reporting that deletion failed. All four original lesson pages reproduced both defects with fictional accounts and local storage.

The existing draft payload already stores every named form field, including intentional empty strings. Restoration now records which owned, string-valued fields were actually restored; cloud answers and profile values fill only absent fields. This preserves existing device-first precedence for nonempty values and extends it consistently to intentional blank values. It does not choose a new cloud revision or conflict policy. Partial, malformed and wrong-owner/course/lesson drafts retain existing safe cloud fallback. Restoration status remains visible, including drafts without a usable timestamp.

Clear still freshly verifies the existing pinned account/session and retires pending saves. If device removal throws, displayed answers remain and status explicitly says the draft could not be cleared. Successful Clear still removes only the current device draft; any existing cloud answers remain unchanged and can load again. The success label says the device draft was cleared without claiming a cloud copy exists; an empty-cloud original fixture reproduced that misleading claim. No cloud delete, new authority or automatic retry is introduced.

Permanent actual-page DOM regressions cover all four lessons, malformed/partial/wrong-owner drafts, successful deletion and cloud fallback. The new exact-source guard checks current source and reproducible 415-file output before executing immutable PR124 and older historical recipes in separate exact clones with real dependency directories and per-entry links. Historical guards, assertions and test outcomes remain unchanged.

Lessons 5–13, original workbook content, private notes/answers, SDK, SQL/RLS, trusted 95% unique eligible watching, multipart 6/8/9 holds, missing videos 11–13 and disabled completion/serving authority are unchanged. Genuine provider latency, remote revision conflicts, real browser/device storage denial and hosted acceptance remain separate limitations. No hosted action, release, messages or payments.

## Submission feedback when device storage is unavailable

Cycle23 reproduced an additional, independent Lessons1–4 feedback defect: the existing `saveDraft()` deliberately allows cloud fallback when browser storage rejects a write, but a later explicit submission failure unconditionally claimed the current answers were saved on the device. A response lost after POST dispatch also produced the same definite-failure/retry wording. Original and independent tests use fictional quota denial, failed HTTP responses and lost replies; no real submission is made.

The correction changes only that catch message. It now says submission could not be confirmed and asks the learner to keep the page open because the current answers may not be saved on the device. It does not assert provider rejection, rollback, an existing durable copy or safe retry. The actual existing device-save/cloud-fallback flow, verified owner/session fences, manual submit control and all data requests remain unchanged. Successful cloud fallback still succeeds despite device-storage denial.

The existing sequence is a user-invoked Netlify Forms POST followed by the fenced legacy Supabase answer/progress writes. It has no combined authoritative request receipt or transaction proving both destinations completed; a read of account answers does not establish the POST's terminal outcome. This message correction does not add idempotency, reconciliation, automatic retry, trusted watch/completion evidence or serving eligibility. Existing hosted acceptance and legacy completion-description limitations remain separately gated.

New permanent tests append to the original reload/clear tests without changing their assertions. They cover all four lessons, absent/older/current device copies, HTTP versus uncertain transport outcomes, successful cloud fallback, account/logout/page retirement and no new submission after a late rejection. All SDK, Auth helper, markup, SQL and Lessons5–13 source remain unchanged. The existing exact-source guard retains its original baseline and predicates; only reviewed changed-file hashes and its manifest pin advance.

## Fail-closed installation contract

The installer requires the reviewed postgres owner, exact canonical dependency table/constraint/trigger/ACL/RLS fingerprints, exact authority helper definitions/owners/ACLs, and the accepted automatic-RLS DDL trigger catalog. It rejects existing or partial Events objects, unknown registry variants, extra DDL event triggers, missing verified-identity shape/capabilities, or catalog drift. Registry profiles are limited to the canonical 27-migration baseline, Forms, Dream Team, and both reviewed Forms/Dream orders. Existing registry and keys are preserved.

All fingerprints use SHA-256 with the same explicit `pg_catalog` search path used during native generation. The full existing application and Storage relation/column/policy/trigger/function/index catalog is compared before and after, excluding only exact newly introduced Events objects. Exact Events table/view/index/function postconditions and the narrowly expected schema ACL change are independently checked. An unrelated `storage.event_history` object remains protected despite its name. Any guard or audit failure aborts the entire transaction; no partial Events schema is accepted.

**Anonymous schema compatibility:** the canonical baseline does not grant anon private-schema usage. Its anon role has zero effective existing private function, relation/view/column or sequence capabilities across all five supported profiles. The installer preserves the exact historical Events `USAGE` grant only after proving this zero-exposure condition, including privileges inherited through PUBLIC or roles. Unexpected existing capabilities, anonymous CREATE/superuser/bypass-RLS authority, private operators or conversions reject installation. This is not permission to broaden a managed provider's Auth ACLs. Historical Events service-role privileges and the public safe event catalog are preserved exactly, not expanded or removed.

## Exact-target release gates and recovery

A target must be separately nominated and its migration ledger/catalog provenance reviewed using the existing metadata-only preflight. Managed `auth.uid()` semantics, managed Auth ownership/effective capabilities, genuine session retirement, PostgreSQL major/catalog representation, encoding/collation and installed DDL extensions remain target-specific facts. Local fictional Auth stubs do not prove provider compatibility. The guarded fingerprint must pass unchanged on that separately reviewed target; mismatch means STOP, never regenerate expected hashes to fit unknown production state.

Require witnessed independent recovery/cleanup, reviewed private credential custody, explicit target plus SQL-SHA installation approval, and genuine isolated Auth/role/revocation/public-catalog acceptance before any hosted installation. `events_catalog` materializes occurrences; never invoke it in a supposedly read-only target preflight.

Before commit, any SQL error rolls back the complete installer. After a separately approved successful installation, do not DROP Events tables or replay a destructive historical uninstall. Disable the new staff/public entry points through a separately approved website rollback and retain records/audits; review a forward corrective migration if needed. Recovery backups and restore scope must be approved and demonstrated for that target. No standalone destructive down migration is supplied, and no hosted rollback has been performed.

# Authorize.Net integration — GIV-3C BUILD ONLY

Sibling of NMI GIV-3B, based on accepted GIV-3A `1410ebc824cdf0b9721c95db0cb41229b74a0274`. No NMI code is copied or changed. No credentials, provider API requests, migrations, deployment or execution activation belongs to this build. Official documentation and official GitHub samples were reviewed October 15, 2026. No third-party payment SDK dependency is added.

## Browser and opaque contract

[Accept.js](https://developer.authorize.net/api/reference/features/acceptjs.html) supports an opaque nonce consisting of `dataDescriptor` and `dataValue`, valid for 15 minutes. The backend adapter accepts only the exact descriptor and a bounded opaque value with explicit owner/person/gateway/environment/expiry scope. It rejects raw payment fields. A token is transient and never a logical saved method. The account that issued it must match the receiving account; no portability is assumed.

AcceptUI requires browser API Login ID. This assignment requires server-only credential handling, so the browser foundation selects [Accept Hosted](https://developer.authorize.net/api/reference/features/accept-hosted.html). Server-side `getHostedPaymentPageRequest` binds canonical amount/currency and an exact approved return URL, disables customer email, and returns only the short-lived form token. The host controller posts that token to the fixed sandbox form URL. Returning from the provider is not payment confirmation; canonical server lookup is required. The module is inert on load, defaults disabled, renders no raw card/bank fields and clears the transient form after handoff/denial. No real component or iframe was loaded during BUILD QA. No CSP relaxation, Accept.js asset or browser API credential was introduced.

## Fixed scoped server transport

Only `https://apitest.authorize.net/xml/v1/request.api` is accepted. Live mode/endpoint overrides fail closed. No default network transport is installed; every call requires an explicit transport, enabled sandbox configuration and a fresh complete accepted 14-gate context. The accepted runtime remains held and unregistered for real execution. Never call this adapter directly from public code or treat caller-supplied booleans as authority. A separately reviewed hosted runtime must resolve the canonical operation lease, current operation-specific permission, frozen route and gates server-side before handoff.

The existing `resolveCredential` tuple checks owner/account/environment/version, then resolves `PAYMENTS_<gateway UUID without hyphens, uppercase>_SANDBOX_V<version>`. The protected runtime value is JSON containing `apiLoginId`, `transactionKey` and optional 128-hex-character `signatureKey`. Only Login ID/Transaction Key go into merchant authentication sent to the fixed sandbox API. Signature Key never goes to a transaction API or browser. No key is read/configured by BUILD. Empty/invalid bindings fail closed, no exception/body is logged, request bodies use strict allowlists, responses are streamed with a 256 KiB bound, redirects are prohibited and timeout means review without automatic retry.

## Transactions and profiles

Current [payment operations](https://developer.authorize.net/api/reference/features/payment-transactions.html): `createTransactionRequest` uses `authCaptureTransaction`, `authOnlyTransaction`, `priorAuthCaptureTransaction`, `voidTransaction`, `refundTransaction`. Exact minor-unit strings become exact decimal strings with BigInt; no float arithmetic or silent FX. Gateway currency/country must match reviewed route configuration. Authorize-only stays authorized; capture is not settlement. Refund approval remains pending until lookup confirms settlement. Refunds use original transaction/account and only allowed last4/masked expiration. Partial/cumulative bounds are enforced. Current approved canonical policy permits authorization voids; captured payments require refund. That restriction is preserved rather than expanding shared policy to all provider-eligible unsettled transactions.

[Customer profiles](https://developer.authorize.net/api/reference/features/customer-profiles.html) use `createCustomerProfileRequest`/`createCustomerPaymentProfileRequest` with opaque input. Safe numeric IDs map to the existing private payment profiles and masked logical method. Logical Visa ending 1111 may have separate Main/Youth/etc customer/payment profiles; they never become cross-account credentials. Duplicate/removed/foreign identity is rejected by accepted canonical attachment checks. Real IDs must never be passed to GIV-3A `synthetic_*` functions or disguised as synthetic evidence. The server mapper defines safe real-reference persistence input; the actual trusted persistence/runtime hookup is a separate hosted gate, not activated here.

`getTransactionDetailsRequest` binds original account and transaction ID, normalizes known states and requires review for unknown/mismatched amount or identity. Safe [error categories](https://developer.authorize.net/api/reference/features/errorandresponsecodes.html) suppress provider text. Duplicate and fraud/unknown results require review; an unproven bank insufficient-funds reason is not invented. Approved AVS/CVV result flags are internal risk-review metadata only; no CVV input or verbose codes reach donor output.

## Recurring and batches

Official [ARB customer-profile sample](https://github.com/AuthorizeNet/sample-code-node/blob/master/RecurringBilling/create-subscription-from-customer-profile.js) confirms `ARBCreateSubscriptionRequest` with scoped customer/payment profile. Weekly/biweekly day intervals and monthly/annual month intervals are modeled; unsupported canonical frequencies fail closed. `ARBUpdateSubscriptionRequest`, `ARBCancelSubscriptionRequest` and `ARBGetSubscriptionStatusRequest` retain the original gateway/instruction/route binding. One canonical multi-fund recurring parent may need several account-specific subscriptions. No schedule is created, due job executed or receipt sent during BUILD.

Official [settled batch](https://github.com/AuthorizeNet/sample-code-node/blob/master/TransactionReporting/get-settled-batch-list.js) and [statistics](https://github.com/AuthorizeNet/sample-code-node/blob/master/TransactionReporting/get-batch-statistics.js) samples define `getSettledBatchListRequest` and `getBatchStatisticsRequest`. Date ranges are bounded, batch identity is checked, known charge/refund amounts are exact and unknown fees/net remain NULL. Batch statistics are reporting observations, never a new ledger or estimated financial truth.

## Signed events and future gate

[Webhooks](https://developer.authorize.net/api/reference/features/webhooks.html) use `X-ANET-Signature`, HMAC-SHA512 over exact raw body using the hex-decoded Signature Key. Verification precedes parsing/lookup/storage. The undeployed default-off handler bounds input and projects only owner/account/event/digest/kind/provider reference/status. Recognized transaction/subscription notifications require same-account canonical lookup and an atomic dedupe store; same ID with changed digest conflicts. No payload/raw credential/card data or authority grant is persisted. Event creation is not proof of financial settlement. The handler deliberately requires injected trusted lookup/persistence; none is deployed in BUILD.

ACH/eCheck remains HELD: this selected host configuration disables bank entry, and no bank object is accepted by the backend. Any later tokenized ACH enablement requires verified eCheck account/capability and its own acceptance; raw bank/routing credentials remain prohibited.

Hosted acceptance must separately authorize protected sandbox keys, exact preview/account binding, trusted canonical operation/profile/observation persistence hookup, actual hosted form/redirect and provider response verification, current grants/revocation, CIM/ARB/capture/adjustments/reporting/webhook delivery and cleanup. BUILD mock evidence is never provider proof. Live activation, real cards/money, receipts, Text-to-Give and GiveHub cutover remain prohibited. NMI hosted acceptance is paused only for NMI credential availability and is not superseded by GIV-3C.

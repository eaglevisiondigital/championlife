# Assigned decision foundation — source only

This is a new, unmounted RPC foundation on PR72 `7699d6cda6309e0d02e1d6058ca1406401a776bd`. It is not the historical `outreach_decision_workspace`/`outreach_decision_access` API, a complete Issue50 release, or an activated host-church portal. No website asset or existing migration changes. The migration filename was generated by installed Supabase CLI 2.81.3 using `migration new campaign_assigned_decision_foundation` (UTC timestamp November 3; local November 2).

## Supported local journey

A separately mapped decision/free-book source and pre-existing explicitly assigned follow-up record can be read by its currently verified, finite, campaign-scoped worker. The worker can update the accepted follow-up status and due date with compare-and-swap revision plus an immutable, atomic retry receipt. Event registrations, waivers, attendance and fundraising are never joined. Follow-up `completed` means the care workflow status, never book/course completion.

The migration introduces no source mappings, assignments, real users, grants or backfill. Without separately reviewed provisioning, the staff result remains unavailable. Existing organization People tasks remain unchanged; this accepted campaign decision workflow does not confer organization People authority.

## Authorization and concurrency

`public.campaign_decision_foundation(p_action text,p_org uuid,p_campaign uuid,p_payload jsonb)` delegates through an invoker wrapper to one private definer with a fixed empty search path. Only authenticated callers receive execute. The helper is not callable by browser or service roles. All new tables have RLS and no direct public, anonymous, authenticated or service-role access. There is no permission writer.

Every staff call requires current `auth.users` verification, an unretired same-user `auth.sessions` row, JWT `session_id` and unexpired JWT `exp`, exact organization/campaign, an active source mapping, and existing assignment with explicit `view` + `decisions.read`, `care_scope=assigned`, and finite decision effective/expiry dates. `followup.manage` and source consent are additionally required to mutate. Organization People, registration, legacy `decision.view/manage`, campaign administrator and Partner capabilities do not substitute. No grant derives from a role label, email, tag or host name.

`FOR SHARE` protects current actor/session/campaign/source/assignment and source registration while an operation executes. Follow-up ownership is checked after its potentially blocking row lock. Current-clock session/grant expiry is checked again after reads/audit work. A caller queued behind revocation therefore denies; revocation queued behind an authorized transaction waits for that transaction. This is database serialization, not cancellation of a result already committed. Consumer-side session/generation retirement remains mandatory before any future mount.

Mutations require an existing positive revision and cannot create or reassign a record. A retry receipt binds exact campaign, record, actor and JSON payload. A changed retry conflicts; an old receipt after a newer revision raises a reload conflict. An audit insertion failure rolls back the update. Audit rows are immutable. A historical record need not be changed merely to appear in this foundation.

## Identity, privacy and truthful status

Detail can project an existing organization Person reference only when the decision source's exact `user_id` equals an active portal account link, the campaign registrant's exact organization/person/legacy-registration IDs agree, the linked Auth account is currently verified, and both initial manual account-link journal and current link journal agree with the stored binding. The positive journal rows are SHARE-locked alongside the registrant, Person, active link and linked Auth account; the baseline journal is not itself immutable, so a deletion/edit must serialize with this projection. The label is `reviewed_existing_account_link`: it reports existing reviewed account linkage, not a new identity verification. It does not infer identity by email/name, create/merge People, or make an optional campaign person ID authoritative alone. Missing, revoked or mismatched evidence yields null Person / `not_linked`.

Names, source decision, registration timestamp, consent and operational follow-up status are projected only for the assigned records. Email, phone, prayer requests, free-text pastoral notes, raw answers, lesson notes, financial data and other-campaign totals are not returned. Contact is always disabled: the advanced adult/guardian provenance package remains paused, so no contact-route attestation, export, contact-history writer or outgoing message is exposed.

`learner_status` requires null organization/campaign and empty payload, and reads only the authenticated owner's enrollment/activity timestamps. It returns `book=not_instrumented` and `completion_authority=unavailable`; client-writable lesson activity is never treated as trusted watch/answer completion. Staff course summary permissions and the later Lockliel trusted completion source are not imported.

## Baseline and source reconciliation

The migration fails before changing anything if accepted decision tables already exist, the exact existing capability CHECK differs, pinned manual account-link/registration/immutable function definitions differ, or required current Auth session primitives/types are absent. It is a forward addition for the measured baseline, not a repair/replay of accepted historical migrations. A different installed decision/Partner/learner schema requires explicit reconciliation, never `IF NOT EXISTS` masking.

The unchanged registration assignment RPC rejects nonregistration requested capabilities and preserves unrelated existing capability keys; it cannot add or remove the new decision capabilities. All previous registration permissions and existing assigned records remain unchanged. PR75's distinct Partner assignment/host issuance logic is not imported or bypassed by this RPC; it supplies no Partner permission or host provisioning path.

Exact source lineage and hashes are in the adjacent JSON. PR35's broad staff, workflows, team/travel, operations, Communications, admin fallbacks and prayer/contact projections were inspected and deliberately excluded. Accepted Issue50 `8afd640` supplies the canonical source/follow-up/audit concepts, assigned-record restriction, atomic revisions and current-clock lock/revocation lessons. New exact scope/current-session/privacy checks are the narrow successor.

## September 27: fresh branch bootstrap repair

**Root cause:** migration `20260923114822_harden_course_security_and_indexes` (second, not third) first references `public.rls_auto_enable()` with REVOKE. The third migration also revokes PUBLIC execution. None of the 17 defines this function. Earlier local replay injected its catalog definition through a test-only fixture, masking the missing provisioning step. Without that fixture, migration two fails with SQLSTATE 42883, exactly as the managed branch does.

**Classification B: project-owned provisioning/bootstrap object, generated by the optional Supabase dashboard setting.** It is not an omitted numbered application migration or an extension-owned/core object guaranteed on every Supabase branch. The original September 23 setup selected “Enable automatic RLS” before connecting the application. The live function is owned by postgres, has no extension membership, and is called by the enabled `ensure_rls` event trigger. Its definition matches Supabase Studio's generated SQL. The original setup record corroborates this; private transcripts are not included here.

Vendor evidence inspected at commit `36371de15127206280d2d40786e8578dfe1b681a`:
- [Project creation form](https://github.com/supabase/supabase/blob/36371de15127206280d2d40786e8578dfe1b681a/apps/studio/components/interfaces/ProjectCreation/ProjectCreationForm.tsx) assigns the template to initial dbSql when enableRlsEventTrigger is selected.
- [Security options](https://github.com/supabase/supabase/blob/36371de15127206280d2d40786e8578dfe1b681a/apps/studio/components/interfaces/ProjectCreation/SecurityOptions.tsx) describes creation of an event trigger.
- [Generated template](https://github.com/supabase/supabase/blob/36371de15127206280d2d40786e8578dfe1b681a/apps/studio/components/interfaces/Database/Triggers/EventTriggersList/EventTriggers.constants.ts) matches the captured helper body and trigger tags.
- [Event trigger documentation](https://supabase.com/docs/guides/database/postgres/event-triggers) presents this as optional setup, not a universally installed object.

`supabase/bootstrap/automatic-rls.sql` restores this project prerequisite separately from numbered migrations. It retains the captured definition and fixed pg_catalog search path, creates the original trigger, and revokes execution from PUBLIC, anon, authenticated and service_role in the same transaction. It neither inserts nor changes migration history. It refuses Auth users, an existing private application schema, migration versions beyond the failed first prefix, unexpected helper definitions/ownership, and unexpected trigger configuration. Repeating it before migration is safe. Historical function error/log behavior is retained for parity; application RLS does not depend on that catch-and-log behavior. Installation failures abort transactionally.

All 17 migration identities, file hashes and SQL remain unchanged. No new forward migration is needed: a migration after the failing second migration cannot provide its prerequisite. Do not invent a backdated version or repair production history.

### Isolated branch procedure

1. Verify branch identity is non-default, parent is the intended project, with_data is false, no Auth users exist, and history is empty or exactly version 20260923114743. Keep preview clients disconnected.
2. In that isolated branch's supported Supabase SQL Editor, run the **complete checked-in bootstrap file** as postgres. Verify the exact branch ref in the URL/header before Run. Never run this against production. This is a reviewed provisioning step, not an untracked workaround or an application migration.
3. For the existing failed branch, use supported branch **rebase** to apply the pending original migrations. Reset/recreate alone repeats the failure because dashboard/MCP branching replays parent history without this project-creation dbSql. A destructive reset may remove the prerequisite; repeat the isolated bootstrap gate afterward if necessary. No production merge.
4. Verify 17 original versions/SQL, 32 public RLS tables, 60 policies, 35 functions, restricted helper execution, and no copied user records. Run security advisors and verify private Data API exclusion before returning to Work.

This is an explicit two-stage initialization contract, not a claim that raw automatic branching now works unaided. Future GitHub-driven provisioning must invoke the same prerequisite before historical replay; seed.sql runs too late. Do not enable a new automation/integration silently.

### Other platform assumptions audited

Managed Supabase supplies anon/authenticated/service_role, auth.users, auth.uid(), and postgres's ability to manage Auth triggers/event triggers. The chain needs no extra application extension: gen_random_uuid is built into current PostgreSQL. All other application schemas/functions/triggers are created in order by the 17 migrations. The regression reproduces the observed branch public default privileges, including non-DML table defaults, instead of assuming blank PostgreSQL defaults match hosted Supabase. It tests both automatic and explicit RLS, exact policy/function parity, and bootstrap refusal paths. Managed Auth/roles and Supautils are not created by the application bootstrap. Final hosted verification remains a separate gate; local tests cannot establish Data API exposure or live Auth behavior.

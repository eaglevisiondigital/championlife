# Campaign task writer contract — held, disposable-local source

## November 6 — canonical audit specification and deferred-fence limits

Baseline: PR106 `07e27b055d49313f2f1c292ae96647f70856be20`, under the source-only assignment in Issue58 comment6676975263. `tools/outreach/task-writer-plan.sql` adds a private, ungranted **held plan**, not an executable writer. It performs no application DML and creates no table, receipt, trigger, migration installer or enablement switch. All PR105 guards and prior source contracts remain unchanged.

The plan receives only the existing exact request. It derives actor/session through preparation, compares the five existing expected revisions under task-first locks, captures the current canonical before-state, and derives the proposed after-state only from the validated status/date intent with one revision increment. It then runs fresh reconciliation, including current dual authority, consent, binding validity and complete canonical-history consistency. Inconsistent history rejects the plan. A caller cannot supply a before-state, actor override or audit specification as authority.

The returned audit specification has exactly the canonical organization/task/server-actor, action `updated`, and the trigger's five before/after fields: `title`, `status`, `due_on`, `assigned_user_id`, `revision`. `expected_event_count=1` is a requirement for the future writer, not a claim an event was written. The observation includes the current PostgreSQL transaction ID as a string. That ID is local diagnostic context: it is neither an operation identity, a signature, a durable receipt, evidence of COMMIT, nor a token accepted by another function. A new transaction recaptures every dependency; no previous plan is consumed as authority.

Every plan returns `HELD`, with `can_authorize=false`, `can_commit=false`, `automatic_retry=false`, and `terminal_verified=false`. The request hash remains only an intent marker. No successful bound task mutation, intent attribution, terminal proof or guaranteed final fence is introduced.

### What the new native proof establishes

The test creates a fictional binding inside a transaction, captures the held specification, and rolls that transaction back. It then independently exercises the existing authorized **ordinary, unbound** canonical task update and compares the actual trigger-generated event against the specification. Three cases cover nullable/date changes and a same-value update. Each appends exactly one event in total, has the exact server actor and before/after fields, and increments the revision once. The ordinary write never receives authority from the discarded plan. This proves correspondence to the actual canonical trigger; it is not positive bound CAS or an atomic transfer from preparation to mutation.

Bound writes are still rejected, and that denial rolls back an earlier ordinary task and canonical event. Stale revisions, wrong actor, caller-supplied snapshots and inconsistent history cannot produce a plan. No application API role receives EXECUTE. Existing function definitions remain byte-identical.

A separate test-only deferred constraint trigger calls the held plan for the bound task while an ordinary fictional task is updated in the same transaction. Its request is captured in the experiment's fixed trigger argument, never a caller-controlled session setting. Under the default deferred mode, session/manage expiry, same-transaction consent or binding withdrawal, follow-up revision drift, and actor/session replacement reject COMMIT and roll back the ordinary task, canonical audit and dependency changes. An independent consent writer waits behind the held authority lock, then becomes visible only after the earlier transaction ends. This demonstrates serialization and rollback mechanics; it does not implement a bound writer.

### Newly demonstrated final-fence gap

`SET CONSTRAINTS task_writer_fixture_final IMMEDIATE` can execute and consume that experimental deferred check early. If the session subsequently expires or the same transaction withdraws consent without another task update, COMMIT succeeds for the ordinary task and its audit. A fresh plan denies access afterward. The permanent tests assert this limitation explicitly, rather than presenting the default deferred result as a guaranteed transaction-end fence.

Thus a deferred trigger alone is insufficient when the caller controls constraint timing or can continue issuing statements after the check. PR105's unconditional bound management denial still blocks actual bound writes in every mode. A future positive writer must have a separately reviewed server-owned transaction lifecycle, including who can issue transaction/constraint commands, how later statements and same-transaction revocation are prevented or fenced, and how any external commit acknowledgment is attributed. Merely adding this experimental trigger or an immediate post-update check is not an accepted solution. No transaction API or operational restriction is invented or installed here.

The plan adds no new row-lock order: it reuses the existing task UPDATE, binding SHARE and authority/dependency locks, then reads protected history under the task lock. A full administrative cross-operation lock-order proof remains outstanding; the narrow native race is not a global deadlock-freedom claim. The existing canonical audit trigger remains the sole future event producer. Any eventual writer must compare exactly one newly appended event and reject missing/duplicate events, wrong actor/scope, unexpected field changes or revision drift within its own transaction before a valid final boundary.

## Next source increment — observational UNKNOWN reconciliation

Successor baseline: PR106 `ccae6ed2d5ca367ce7e249e6fd3d3d795b4297c3`. The new `tools/outreach/task-writer-reconcile.sql` adds only a private, ungranted function for the disposable fixture. Reconciliation validates a contiguous canonical event chain: one event per task revision, a creation event whose actor matches the canonical creator, exact predecessor snapshots on later updates, and a final snapshot equal to the current canonical task. Missing, duplicate or inconsistent history yields `CANONICAL_HISTORY_INCONSISTENT` without a task projection. Consistent history yields `EXPECTED_REVISIONS_CURRENT` and only the neutral task ID/status/date/revision and already validated revision expectations. Stale expectations raise `40001`; invalid scope or current authority raises `42501`; malformed requests remain rejected. The existing outcome classifier preserves `UNKNOWN` for all of these outcomes.

Canonical history has no durable intent UUID or request digest. Matching status/date/revisions/history therefore cannot attribute an event to this request, prove a request completed, exclude a pending operation, establish that a write never committed, or clear an uncertain outcome. An absent event is not a negative commit receipt. Changing the payload under an existing intent UUID remains neither replay detection nor idempotency. The function creates no receipt registry, transport, retry port or permission to resubmit.

The exact input and authority checks remain those below. No preparation or reconciliation response can be supplied as authority to another operation. This increment closes the missing fresh observation path; it does not complete the atomic bound writer.

### Lock and transaction-boundary evidence

Preparation and reconciliation acquire the task UPDATE lock before the binding SHARE lock, then use the existing helper's session/directory/permission/campaign/assignment/source/follow-up/registration/identity/evidence locks. Event and financial/tag attachment guards acquire the task UPDATE lock first, so reconciliation does not add an event-to-task lock inversion. The task lock stabilizes its protected event history while reconciliation reads it. Binding insertion also takes the task lock; binding withdrawal changes only the binding and its own audit. These statements describe the inspected paths, not a completed proof of every administrative cross-operation lock order. Deadlocks/timeouts still fail closed as UNKNOWN without automatic retry.

New native tests demonstrate an actual independent task lock wait followed by committed consent revocation, and a concurrent event insertion blocked by reconciliation's task lock then rejected by the unchanged bound-event guard. No trigger, RLS definition or grant is disabled to create these cases.

The existing PR105 deferred `campaign_bound_task_commit_fence` is exercised by updating an ordinary synthetic task, then adding its fictional binding within the same transaction. COMMIT rejects and rolls back the task change, canonical event, binding and binding event. The same denial holds after fixture binding expiry or consent withdrawal. Because the guard unconditionally denies bound management, these are negative transaction-end tests, **not positive proof that an authorized bound write survives until a fresh expiry/consent check**.

An additional executable limit is deliberate: a reconciliation-only transaction can COMMIT after the session expires because a read does not queue a task constraint-trigger event. The prior observation stays UNKNOWN and a fresh reconciliation denies access. Same-transaction consent withdrawal is also denied on a fresh check. Changing constraint mode to IMMEDIATE does not open the bound writer. There is still no implemented positive bound mutation/audit/final-fence sequence.

## Exact request and server checks

The strict request contains actor/session IDs; organization, campaign, registration, Person, account, task and binding IDs; an intent UUID; exact source string; five positive integer expectations (`task_revision`, `binding_revision`, `campaign_registrant_revision`, `portal_link_revision`, `followup_revision`); and only `status` plus nullable ISO `due_on`. Unknown keys, malformed IDs/dates/revisions and non-neutral intent fail closed. Actor/session fields bind the intent to server-derived Auth identity; they never grant it. SQL receives an immutable value and normalizes the accepted date/status before returning the held intent. The request SHA-256 is an intent/change marker, not evidence verification or a durable receipt.

Task row UPDATE lock precedes binding SHARE lock. This agrees with PR105 binding insertion and task-audit/financial/tag attachment ordering and avoids task-lock promotion after binding locks. The unchanged access helper obtains its existing authority locks; the contract additionally requires current, unrevoked, organization-wide `followup.manage`. It derives actor/session through the existing Auth helper, verifies the exact bound scope, fixed neutral task, independently current People/read/manage authority AND exact assigned campaign follow-up authority, consent, source mapping, account/Person link and verified-adult finite binding. Every expected revision is compared under these locks. Original registration and campaign source mapping have no fabricated revision: their current source/account/consent/active values are checked by the existing helper. Identity evidence versions are not interchangeable with record revisions.

After all potentially blocking lock acquisitions, it rechecks authority/session and wall-clock permission/assignment/binding validity. Held preparation takes row locks, so an enclosing transaction must end promptly. A returned preparation is only an observation within its transaction, never a transferable authorization token. Any future writer must perform its entire check/update/audit/final-fence sequence within one server transaction; it cannot trust this response as authority.

A valid request returns `state=HELD`, `can_authorize=false`, `can_commit=false`, `automatic_retry=false`. The outcome classifier contains no transport or write port. Unrecognized, failed, timed-out, deadlocked, stale or apparently successful outcomes become `UNKNOWN` with no automatic retry. An intent UUID is not an idempotency guarantee. Fresh read-only reconciliation is required after uncertain outcomes; this package has no replay mechanism.

## Mutation contract still required before enablement

Separately accepted provenance producer/custody, finite validity and independent reviewer designation are prerequisites. No current hash/reference or role name substitutes. A separately reviewed future implementation must atomically compare all expected revisions, update only the canonical task status/date, increment the canonical revision through existing semantics, append exactly one immutable canonical event with server actor and exact before/after intent, and run a final consent/revocation/expiry fence. Audit failure, stale dependencies or final-fence denial must abort the complete transaction. Binding creation, reassignment, task issuance and contact authority remain separate held scopes.

This increment cannot exercise a successful bound UPDATE without weakening PR105's deliberate unconditional manage denial. It does not do that. It proves the compare precondition and serialization only; **transactional bound mutation CAS, positive bound audit and a bound post-update commit fence remain unimplemented and unverified**. There is no committed-write receipt to reconcile. A future commit-time expiry check and full cross-operation lock-order review are required before any writer exists.

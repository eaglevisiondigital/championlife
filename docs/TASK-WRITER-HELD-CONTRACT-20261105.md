# Campaign task writer contract — held, disposable-local prototype

Exact base: PR105 `403b6d6624c0e182fecaab16a57261b900142a4b`. This source increment implements a server-owned **prepare contract**, not a successful task writer. It does not install a migration or expose a public/API method. Actual campaign-bound mutations remain disabled by the unchanged PR105 policies and guards. No production issuer, source binding producer, reviewer designation, runtime mount, bypass flag or activation switch exists here.

`tools/outreach/task-writer-prepare.sql` is loaded only by a disposable PostgreSQL test fixture. Its private function has no EXECUTE grant for PUBLIC, anon, authenticated or service_role; local tests call it as the synthetic fixture owner with fictional current Auth claims. It creates no table, replaces no function, and performs no application DML. It is not a deployment artifact or authorized hosted SQL.

## Exact request and server checks

The strict request contains actor/session IDs; organization, campaign, registration, Person, account, task and binding IDs; an intent UUID; exact source string; five positive integer expectations (`task_revision`, `binding_revision`, `campaign_registrant_revision`, `portal_link_revision`, `followup_revision`); and only `status` plus nullable ISO `due_on`. Unknown keys, malformed IDs/dates/revisions and non-neutral intent fail closed. Actor/session fields bind the intent to server-derived Auth identity; they never grant it. SQL receives an immutable value and normalizes the accepted date/status before returning the held intent. The request SHA-256 is an intent/change marker, not evidence verification or a durable receipt.

Task row UPDATE lock precedes binding SHARE lock. This agrees with PR105 binding insertion and task-audit/financial/tag attachment ordering and avoids task-lock promotion after binding locks. The unchanged access helper obtains its existing authority locks; the contract additionally requires current, unrevoked, organization-wide `followup.manage`. It derives actor/session through the existing Auth helper, verifies the exact bound scope, fixed neutral task, independently current People/read/manage authority AND exact assigned campaign follow-up authority, consent, source mapping, account/Person link and verified-adult finite binding. Every expected revision is compared under these locks. Original registration and campaign source mapping have no fabricated revision: their current source/account/consent/active values are checked by the existing helper. Identity evidence versions are not interchangeable with record revisions.

After all potentially blocking lock acquisitions, it rechecks authority/session and wall-clock permission/assignment/binding validity. Held preparation takes row locks, so an enclosing transaction must end promptly. A returned preparation is only an observation within its transaction, never a transferable authorization token. Any future writer must perform its entire check/update/audit/final-fence sequence within one server transaction; it cannot trust this response as authority.

A valid request returns `state=HELD`, `can_authorize=false`, `can_commit=false`, `automatic_retry=false`. The outcome classifier contains no transport or write port. Unrecognized, failed, timed-out, deadlocked, stale or apparently successful outcomes become `UNKNOWN` with no automatic retry. An intent UUID is not an idempotency guarantee. Fresh read-only reconciliation is required after uncertain outcomes; this package has no replay mechanism.

## Mutation contract still required before enablement

Separately accepted provenance producer/custody, finite validity and independent reviewer designation are prerequisites. No current hash/reference or role name substitutes. A separately reviewed future implementation must atomically compare all expected revisions, update only the canonical task status/date, increment the canonical revision through existing semantics, append exactly one immutable canonical event with server actor and exact before/after intent, and run a final consent/revocation/expiry fence. Audit failure, stale dependencies or final-fence denial must abort the complete transaction. Binding creation, reassignment, task issuance and contact authority remain separate held scopes.

This increment cannot exercise a successful bound UPDATE without weakening PR105's deliberate unconditional manage denial. It does not do that. It proves the compare precondition and serialization only; **transactional bound mutation CAS, positive bound audit and a bound post-update commit fence remain unimplemented and unverified**. There is no committed-write receipt to reconcile. A future commit-time expiry check and full cross-operation lock-order review are required before any writer exists.

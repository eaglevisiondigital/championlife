# Scoped admission and canonical event experiment

Base: PR106 `9fa39bd9ae46624f5f20617218db0a42891750ee`. This implements the disposable admission investigation authorized by [Issue58 comment6679955886](https://github.com/eaglevisiondigital/championlife/issues/58#issuecomment-6679955886). It extends the existing `task_intent_fixture` experiment; it is not a migration, operational registry, task writer or terminal result API. PR105's unconditional bound-task denial, existing five-revision held plan and outcome classifier remain unchanged. RELEASE NO-GO.

## What changed and what the experiment assumes

The earlier fixture could reference an unrelated old event through its receipt foreign key. A rollback could also remove a request without excluding a later execution. The extension in `tools/outreach/task-admission-proof.sql` adds two executable restrictions to that same fixture: correspondence with the actual canonical event observed during an armed transaction, and serialized closure of an existing admitted intent within the named lab paths.

Existing immutable `intents` remain the admission records. Two new fixture tables retain execution observations and immutable settlements. The experiment assumes the reviewed schema/triggers are intact, the fixture owner runs the documented paths, one ordinary task is armed per transaction, and a task attempt holds its acquired locks through COMMIT/ROLLBACK. The owner can change schema or issue unguarded SQL; this fixture cannot establish a trustworthy operational security perimeter. There is no runtime mount, API privilege, production state, cancellation endpoint or retry loop.

The existing capture helper derives actor/session through the server Auth helper and task/organization/Person from canonical rows. It retains exact status/date/revision identity and refuses bound tasks. `arm(intent_id)` accepts only an already-existing admission, current original actor/session and existing ordinary task authority, with the expected ordinary revision still current. It does no canonical task DML. The native harness then updates the ordinary canonical task through the unchanged task guard and audit trigger.

The added event INSERT observer runs beneath that canonical audit trigger. For an armed task in the current transaction it compares the exact organization, task, server actor, action, before state and after state, including one revision increment, title, assignee, status and nullable date. It inserts the existing fixture receipt and a `LAB_EVENT_OBSERVED` settlement together with the actual event. The caller cannot nominate an old event. Direct insertion of a matching event or receipt fails the expected trigger nesting; mismatched mutation and a second update fail and roll back the containing transaction. Existing canonical function definitions are unchanged; this is additional disposable instrumentation, not a replacement audit producer.

The transaction ID selects the current observation only. It is not a receipt, authorization credential or proof of durability. Trigger depth constrains this reviewed call graph, not arbitrary triggers installed by an owner. A transaction may arm and commit without an event; that creates no observed-event settlement. Its outcome remains unresolved. Existing historical fixture receipts are not validated or adopted by this extension.

## Locking and scoped closure

All new paths retain the original task-first order. They first read the immutable admission solely to locate its task, call the existing capture checks while locking that task, then lock the admission row FOR UPDATE. No path locks an intent and subsequently acquires a different task. Capture's task → uniqueness/intent SHARE order is preserved; a conflicting UUID proposal for another task eventually fails its exact tuple comparison. The tests cover this collision while rejection holds the existing admission lock. They do not establish the complete production administrative lock graph or arbitrary multi-task transaction ordering.

`reject_admission(intent_id)` requires the same existing admission and current original identity/ordinary authority. It takes the same locks as arm and records `LAB_REJECTED` only if no event result already exists. Missing admission cannot be turned into a rejection. A pending armed execution blocks rejection; after execution commits, rejection fails, and after execution rolls back, rejection may proceed. Conversely a pending rejection blocks arm; a committed rejection denies it, while a rolled-back rejection allows the waiting attempt. Subsequent arm cannot execute either settled lab intent again. Repeating the same rejection is observationally idempotent.

Those guarantees hold only for these lab paths and their retained admission row. They are not cancellation of arbitrary in-flight database work, provider completion, no-pending proof, production idempotency policy or permission to repeat a request. The native counterexample explicitly commits an ordinary direct update after `LAB_REJECTED`: writers that never arm do not consult this fixture. The unchanged classifier returns UNKNOWN/no automatic retry for both lab observations and independent snapshots.

## Final authority and production gaps

An observed canonical event is still not a transaction-end authorization fence. The native suite updates an ordinary task, obtains its lab receipt, then revokes the session in the same transaction and commits. That intentionally passing counterexample proves the event-time check cannot protect later changes. The prior SET CONSTRAINTS early-fire counterexample remains accepted evidence and is not duplicated or bypassed here.

Only ordinary fictional tasks provide positive controls. This extension does not perform a five-revision bound CAS, establish real independent reviewer/provenance custody, approve a final expiry/consent veto, or settle an actual uncertain request. The existing held plan continues to check server actor/session, exact scope, five revisions and current dual authority without authorizing a write. No new false authority flag wraps that unresolved implementation.

An operational design still requires every permitted execution and administrative path to obey an accepted complete lock/exclusion protocol; exact trusted request-to-event custody; a transaction-end authority boundary that cannot be forced early or bypassed by later same-transaction changes; independent current-authorized reconciliation; and accepted retention/namespace retirement without re-admission. Actual reviewer/authorizer designations, source/identity/adult/consent methods and finite custody/retention values remain owner decisions. The global UUID and same-session rules here remain conservative lab assumptions, not new product policy. Provider/R5 terminal guarantees remain external and unproved.

## Validation

Run `node tools/outreach/task-admission-proof.native.mjs` with the existing cached test dependencies and PostgreSQL17. The script creates and destroys its own Unix-socket database. No hosted URL, real account, message, provider, permission grant, public asset or deployment is used.

The focused suite covers actual trigger correspondence and one-event count; old-event/direct-event/result injection; changed status/date/title/actor; extra update; immutability and role denial; independent visibility; four competing execution/rejection commit/rollback outcomes; different-task UUID contention; timeout followed by blocker commit; session revocation during a real task-lock wait; unchanged bound task/history; and the final-fence/outside-path counterexamples above. Original setup failures are preserved privately; independent review and exact-head CI are separate from the author run. Prior accepted suites are not counted again.

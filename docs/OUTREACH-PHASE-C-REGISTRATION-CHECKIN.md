## Shared model and identity

Organization → existing Outreach Campaign → event registrations → individual attendees → exact waiver coverage and attendance. This is a registration submission model, not another canonical People or Household database. Submitted names/contact, original request payload, campaign/source/time/reference and separate consent choices are private. `household_id` and attendee `registrant_id` are reserved scoped links for later reviewed canonical linking; no public input populates them. No automatic email/phone matching, Person creation, membership, course, finance, staff or portal authority is granted. Existing Phase A reviewed identity pathways remain the canonical authority. Separate repeated household entries with different request identities require review; contact similarity is not identity proof.

`outreach_event_registrations` holds one household submission and a random `R-` reference. `outreach_event_attendees` holds distinct adult/minor entries, client identity keys, name/age/relationship, guardian description, attendance, configured prize preferences/answers, staff operational notes/wristband and authoritative check-in actor/time. One household may include self, spouse, child, dependent and other adults. Under-18 entries require child/dependent relationship plus guardian description. Stable member keys deduplicate retry/add operations within a registration; same-name twins are not silently merged. Each registration is attached to its owning campaign and Organization by foreign keys.

Status: submitted, confirmed, checked_in, cancelled, no_show, closed. A household marked checked_in still has individual attendance states; preregistration is never proof of attendance. Closing/cancelling beneath an active check-in is rejected; staff must reverse those states first.

## Public route and ingress

Reusable shell: `/outreach-register.html?campaign=<public-slug>`. A slug is configuration, not a schema or separate city implementation. Champion Life/SowGo use their existing approved logo assets; other Organizations use their own name rather than inherit another product’s logo. Future campaign aliases can target it after approval; no `/huntsville/` alias or Bessemer rewrite is added now. Campaign config defaults disabled, requires an eligible campaign lifecycle/window and, when waiver is required, an effective published version. Public projection contains only owning organization name/approved existing logo asset, event name/time/timezone, venue name/address, configured questions/prize guidance, instructions and waiver text/version. It never returns household/attendee/signature records or private venue/settings fields.

Anonymous `outreach_registration_config` is an intentionally narrow read-only definer with an empty search path; guests get no private-helper execution/schema privileges. Submission is only through `supabase/functions/outreach-registration-submit`. Dedicated fail-closed configuration uses existing trusted `cf-connecting-ip` ingress normalization/HMAC, strict allowed origins, Turnstile action `outreach-registration`, expected challenge hostname, bounded streamed JSON and timeout. Only the server service credential can execute `outreach_registration_gateway`. The UI never receives it; no sign-in/account is required. SQL has an independent hourly network guard (120 attempts, matching the existing Outreach network ceiling). Invalid submissions consume this quota too. Production ingress, retention and thresholds still require release review. Do not expose the gateway using a client-selected IP/header trust fallback.

The gateway requires `OUTREACH_REGISTRATION_TURNSTILE_ACTION` plus existing server URL/key, pepper, challenge secret/origin/hostname configuration. Its `index.ts` and gateway module are committed but **not deployed**. A separate JWT-disabled guest Edge deployment is needed after isolated acceptance authorization, preserving its own Turnstile/CORS/server gates. Existing partner gateway is not modified. Hosted dummy challenges are accepted only in acceptance mode for the exact acceptance project; production dummy keys fail closed.

Idempotency: campaign + random request UUID, exact payload comparison, campaign row serialization. Retry returns only accepted/reference/attendee count. Changed payload under the same key is rejected. Browser session storage holds only non-secret random request/signature/member keys, never family PII. In-page network ambiguity freezes the payload for an exact retry; keys survive refresh so reentered original values can retry safely. Browser storage is not an offline-sync engine or a private-data cache. Successful submission clears these keys. The reference is a staff lookup hint, never a bearer credential/public read capability; no public lookup/list/detail endpoint exists.

## Waiver and signature contract

`outreach_waiver_versions` is immutable, with reusable template key, campaign, version, effective timestamp, exact text and publisher. No production waiver wording is invented or seeded. The admin publishes reviewed text and may publish a new immutable version; prior signed text is never rewritten. New signatures require the currently effective version; exact retries of existing signatures remain idempotent after a later publication.

One adult/guardian types a legal name and explicitly acknowledges both text and authority for the selected attendees. Coverage keys must belong to that household; required campaigns cover all attending members. Minor coverage requires parent/legal_guardian. A self signature covers only its named adult signer. Other selected adult coverage is an explicit signer-authority assertion, not inferred from a shared surname/household. This is a typed-name event acknowledgment, not verified legal identity, pickup authority, notarization or a third-party legal-grade e-sign product.

Signatures snapshot exact text/version, name/relationship, method, timestamp, recorder and selected attendees' identities/ages/guardian relationships. Update/delete is prohibited even through privileged table writes. Staff correction appends an immutable invalidation with reason/actor/time; new signing is a new record. Active check-ins must be reversed before invalidating coverage. Changing an attendee's signed identity makes old coverage invalid for that current attendee without changing the historical snapshot. Template publication alone does not retroactively invalidate unchanged covered attendees. No drawing image/biometric collection is added.

Event waiver, ministry follow-up, event communications, marketing and media choices are independent and default to no consent. Registration does not imply communications/marketing/media permission or send a message. Exact consent wording and legal text are pending source/policy approval before any campaign activation.

## Staff operations and permission boundaries

`/staff-outreach-registration.html?campaign=<campaign-uuid>` extends the black/white/gold staff workspace; campaign overview links to it. Without a campaign it lists only authorized campaigns. RPC `outreach_registration_workspace` supports campaigns/context/list/detail/configure/waiver_publish/access/walkup/update/attendee_add/attendee_update/sign/waiver_correct/checkin/reverse/csv. All private implementation helpers remain revoked from callers except the authenticated guarded workspace entry and server-only gateway entry.

Existing verified, active, effective, unexpired campaign assignments require `view` and `registration.view`. Independent capabilities are `registration.manage`, `registration.export`, `checkin.manage`; each requires registration.view. Existing explicitly provisioned campaign administrators retain reviewed admin operations through current staff assignment checks. Registration capabilities neither grant nor inherit People/finance/staff/course/travel authority. Local pastor follow-up alone cannot read registrations. Configuration, waiver publication and registration capability changes require campaign administrator manage; capability changes preserve all other grants, dates and active state and require revision/reason. No account/grant is seeded.

Lookup by reference/primary name/phone/email is campaign-scoped. Detail includes only registration identity, contact, members/ages/guardian description, coverage/signed status, source, separate consent values, operational notes and prize/check-in state; no unrelated Person fields/course answers. Manage staff update household/member records, add/remove members, record signatures/corrections, and create walk-ups with the same schema/editor. Walk-up submission opens that household for individual check-in; it is not automatically present.

Check-in staff review each attendee/coverage, optionally record wristband/reference, then check in that individual. Required coverage, active/attending state and open registration status are checked server-side. Retry keeps one state and one event. Reversal requires an explicit reason, preserves history and clears current prize eligibility. Checked-in identities cannot be edited until reversed. Authentication/access loss clears protected DOM, discards stale responses and denies subsequent requests in the same session. Return-to-staff/login routing reuses existing same-origin routes; no Auth configuration is altered.

## Prize and communications boundary

Campaign-configured prize IDs/labels/guidance drive bike interest, tablet-only and other mapped answers; no A–H enum. Attendee → nullable existing campaign registrant prepares future decisions/follow-up. Check-in → existing dormant `outreach_prize_participants.attendee_id` unique link reuses the Phase A prize identity; it does not create a separate ledger. Check-in presence, current waiver and opt-in define the Phase C eligibility projection. Reversal deactivates that dormant participant. No drawing number, pool entry, draw, wheel or prize win is created. Final one-person review/drawing behavior remains Phase D.

Held hooks: `outreach.registration.submitted`, `outreach.registration.updated`, `outreach.waiver.signed`, `outreach.registration.confirmed`, `outreach.attendee.checked_in`, `outreach.attendee.checkin_reversed`, `outreach.walkup.registered`. Meaningful actions append existing campaign audit records with subject IDs/count/version/source/reason, not raw contact or signature content. No SMS/email/provider worker or Communications Core is added.

## Export, privacy and degraded operation

Explicit registration.export authorizes a scoped CSV with reference/primary/attendee/age/adult-minor/guardian/phone/email/waiver/check-in/source/prize choice. Cells use existing spreadsheet formula neutralization. Signatures, raw UUIDs, idempotency keys, notes and unrelated campaign data are omitted. The private printable backup roster requires export permission and records an export audit event; it includes household/reference, attendee/age, guardian/phone, coverage, check-in and prize choice. Staff must handle printed/exported minors' data privately.

Every new public table enables RLS and revokes raw anon/authenticated privileges; invoker staff/server entrypoints call fixed-search-path guarded private definers. Signatures and corrections are immutable. Public references/guessed attendee IDs never authorize reading. Real future offline/degraded synchronization needs separately designed conflict reconciliation; Phase C provides authorized export/print fallback only, not offline write/sync.

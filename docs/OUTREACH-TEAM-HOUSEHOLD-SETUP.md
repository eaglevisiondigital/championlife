## Review before creating or adding facts

Only a reviewed minor's Team screen offers **Review canonical Household setup**, and only after a current canonical `staff_workspace_context` response confirms the exact organization and organization-wide `people.read`, `households.read` and `households.manage`. Scoped arrays, other organizations, missing grants, changed sessions or failed checks never qualify. The same gate runs before/after canonical reads and inserts. Reviewer, organization, view generation and query/selection version bind every asynchronous result.

The setup screen explicitly states that names and `adult`/`child`/`other` labels are factual Household records, **not legal guardian authority, identity merging, account access or travel approval**.

1. Search by a manually entered Household name, bounded to150characters. Matching labels are possible matches only. A full26-result page requires refinement before a new Household can be created.
2. Select and review an existing Household, including its actual active/archive state and existing Person names, labels and active/inactive membership states. Archived Households have no mutation controls. Existing memberships, including inactive ones, are retained and excluded from duplicate insertion; this screen never relabels, reactivates, moves, archives or restores them.
3. Alternatively choose **Create a separate Household after match review**. Its name starts blank, is trimmed/bounded to150characters, rejects controls and requires an explicit match-review checkbox. The insert contains only `{organization_id, name}`; server defaults establish identifiers, active status and revision. Saving a Household adds no membership or guardian record. Selecting **Review created Household** is a separate action.
4. Add one reviewed membership at a time. Explicitly choose this minor or an already reviewed/approved adult Team participant, choose a factual label and check the Household/Person/relationship review checkbox. No selection or label is defaulted from an application, age, shared surname/email or companion string. Other arbitrary people/roles and injected identity/active/archive fields are not accepted. The only insert payload is `{organization_id, household_id, person_id, relationship}`.
5. **Return to guardian authority review** refreshes the Team record and existing `guardian_options` form. Only the separate existing **Save verified guardian authority** command with its selected approved adult/Household and explicit reason invokes `guardian_review`. Setup never invokes that command automatically or updates the Team member's guardian/Household fields. Backend eligibility, active-travel correction refusal and full itinerary validity remain unchanged.

This interface is additive only. Correcting an existing inactive/incorrect membership or archived Household requires separately authorized trusted review; there is no silent repair, upsert, destructive rollback or new policy here. Simultaneous names are not deduplicated automatically. Existing composite foreign keys and membership uniqueness remain authoritative.

## Protected API and failure boundaries

Every read is filtered to the current organization. Household/member return projections contain only operational canonical fields; member-name lookup reads only Person id/organization/name. A selected active Household is re-read before membership insertion and observed revision/state drift refuses the action. Existing membership is checked again immediately before insert; a newly observed row is retained rather than overwritten. The existing server trigger locks the active parent Household and its RLS/column grants/foreign keys/unique constraint/audit triggers remain unchanged. The later People migration's effective-permission view rewrite and own-permission RLS compose with the historical Household guards; reading the older guard body in isolation is not the final permission contract.

Client scope/revision checks are separate network requests and cannot provide a database-atomic authorization/revision promise. Original helper time semantics remain unchanged. The protected API remains authoritative; a request already accepted cannot be undone by a later session change. Late or revoked responses cannot restore protected content or offer legal-guardian confirmation.

Each insert consumes its create/add form before sending. Errors/timeouts, missing/malformed/cross-organization results and concurrent uniqueness/archive failures require a fresh search/review; the UI neither retries automatically nor asserts that nothing committed. Raw provider/SQL errors are never shown. Creating the Household and its two memberships are separate explicitly reviewed transactions: if a later step fails, prior canonical rows and audit remain; no compensating delete/update is attempted. A Household may therefore remain empty or partly populated pending review. No guardianship/travel claim follows from a partial setup.

Search/read bounds are26Household matches and at most100existing memberships. If a Household exceeds the review bound or canonical names cannot be confirmed, no membership form is exposed; this is a UI review limit, not a new database size policy.

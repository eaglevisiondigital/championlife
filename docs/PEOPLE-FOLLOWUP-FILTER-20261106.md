# Filter an existing Person’s follow-up tasks

Source-only increment from accepted People/Outreach PR72 `bf4cf916f176ae8c1e86401c64306c56cfca6a35`. A Person with many completed tasks previously required paging through those tasks to reach older open work. **Task status filter** now offers **All tasks**, **Open tasks**, **Completed tasks**, and **Canceled tasks**, using the existing canonical status values and task read authority.

The filter is applied by the existing Supabase query before the 101-row keyset lookahead. Each page still displays at most 100 tasks ordered by `created_at DESC, id DESC`. This is an authorized live view, not an export, frozen snapshot or task count. No date interpretation, overdue policy, identity association, assignment or new permission is introduced.

All remains the default. Changing the filter returns to its first page. Older/newer navigation, latest refresh, status/date edits and uncertain-save review retain the chosen filter. Completing an open task removes it from Open results after the fresh read; a later page may become empty and retains its existing route back to newer tasks. Empty first pages identify the selected status. Successful task creation retains the established return to latest All, making the newly created open task visible even when creation started from Completed or Canceled.

The filter is held only in the current Person-detail closure: no URL, localStorage or sessionStorage state. Returning to People or reopening a Person starts at All. Account/organization/navigation retirement follows the existing protected workspace lifecycle. Retained detached handlers cannot request a previous Person. The new control also captures account, organization, Auth/client/auth-object identity, route and shell state; a changed still-connected context retires the control without initiating a read. Only the four allowlisted values can start a query. The detail load captures that same context and checks it after every asynchronous stage, before the task query and before rendering. A context replaced while a response is pending invalidates the detail generation and clears the view; its old rows cannot be reattached. The retirement check also runs when an awaited request rejects, so an error cannot leave a previous Person heading behind after context replacement. This does not retrofit unrelated legacy controls or claim instantaneous cancellation of a previously submitted HTTP request.

Existing current-session checks and People/follow-up permission refreshes precede reads, with a final permission refresh before task rendering. Existing RLS remains authoritative for organization, Person and independently scoped financial tasks. Read-only staff can filter without management permission. Updates retain exact organization/Person/task/revision filters. No database migration, RPC, RLS, grant, SDK, public manifest, branding or other public asset changes. The accepted recent-history helper is byte-identical; its validation, projection and 50-event display limit are preserved.

# Existing worksheet backend integration

The isolated worksheet reader uses the existing Supabase client and owner-only course_enrollments/lesson_answers tables. It does not create an enrollment, answer, identity, Auth instance, store, grant, migration or public route. Exact nonproduction project, Auth and REST URLs and client object identity are checked before and after asynchronous work; the known production project is rejected. Session events synchronously invalidate the generation, abort available SDK reads and clear the consumer's presentation callback. Provider getUser checks captured identity and verified email before/after reads; retained old responses cannot return data after session transitions. Account/campaign selection cannot be passed as worksheet identity.

The reader returns only the number of saved nonblank answers, never answer text, identifiers or errors. The reviewed HTML inputs currently enumerate twenty questions on each of lessons1–4; a source regression binds that inventory. Lessons5–13 do not acquire fictional cloud worksheets. Existing RLS remains the database authority, with native PostgreSQL tests using unchanged migrations and fictional authenticated claims.

This is observational saved-answer status, not assessment, video evidence or permission to complete a lesson. canComplete and canCommit stay false. Existing answers are mutable and browser-writable under owner RLS; updated_at is client-controlled and is NOT an authoritative revision. A future progression write requires a serialized backend transaction binding its exact current worksheet, enrollment, session and independently verified playback evidence. No video provider has been approved here; a signature over client telemetry does not establish actual watching. No new provider receipt schema is invented. Public activation, genuine provider session revocation and completion writes remain separately gated. The existing King Kind migration hold, reader, notes, course progress and SDK bytes are untouched.

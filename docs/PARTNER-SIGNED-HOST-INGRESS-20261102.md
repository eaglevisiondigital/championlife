## Integrated source contract

`createCanonicalPartnerHostIngress` in `tools/partner-platform/canonical-host-ingress.mjs` accepts trusted host construction inputs: an exact HTTPS issuer ending `/auth/v1`, one public ES256/P-256 JWK with explicit `kid`, and an exclusive database connection acquisition function. These are not HTTP/request configuration. It imports the official `@supabase/auth-js` **2.118.0** SDK, matching the site's existing SDK version; an isolated package/lockfile pins it and its only dependency, `tslib` 2.8.1. No shared frontend or backend package changes.

Each read accepts only a bounded access token, organization, campaign and assignment UUID plus its transport AbortSignal. The SDK's actual `getClaims` verifies the signature using the trusted public key. A narrow header check permits only ES256/JWT/the known key ID; embedded keys, key URLs, critical headers, unknown keys and HS/none algorithms deny. The SDK has no stored session, refresh loop, browser URL handling or network fetch; its cache namespace is private to the ingress instance. Missing WebCrypto fails construction. Neither SDK discovery nor fallback to Auth `getUser` may authorize a request.

Verified claims must carry the exact issuer, authenticated audience/role, nonanonymous status, valid UUID subject/session and integer issued/expiry/not-before bounds. Audience arrays and unsupported signing algorithms are held, not automatically admitted. Signed role/audience are token-type restrictions, never record authority. Email, names, tags, `user_metadata`, `app_metadata`, donor status and requested Person IDs do not grant access or link People.

Each read creates an immutable principal and its own restricted repository/identity adapter. It passes only verified subject and session into the existing transaction. The **unchanged** current database checks still enforce current Auth user/session, session-user pairing, account linkage, campaign and Partner permission, assigned worker/record, consent and exact Issue50 source/review/receipt/audit provenance. No caller can pass `verified`, `userId`, `sessionId`, a verifier, a manifest or a repository. No duplicate user or Person store is created. Only `{identityStatus, personId}` can leave the adapter; errors use the existing null/unverified result and are not logged.

## Lifetime and least privilege

The configured `acquire({signal})` must return a fresh/exclusively owned connection with `query` and `release(discard)`; discard must destroy it and release locks, including a blocked query. It receives neither token nor caller-selected SQL, credentials or principal. Transport abort destroys that lease once; expiry is checked around database operations and again before returning. Failure and rollback cannot recycle claims into another request. Concurrent requests have separate principal objects and leases.

`retire()` permanently denies new reads and aborts all in-flight reads for that issuer instance. The public key is copied at construction; later configuration-object mutation cannot silently rotate trust. Unknown `kid` is always denied. A future approved rotation must validate replacement issuer/public-key custody, construct its replacement instance and retire the old one; there is no automatic fetch, indefinite cached-key promotion or key-removal bypass. No rotation policy, actual key or provider signing configuration is selected by this source package.

The existing strict profile still checks all **23 function / 17 relation** pins, requires absence of both historical authenticated private-writer EXECUTE grants, and requires the unchanged NOLOGIN/no-members execution envelope before/after the read. This successor changes **zero SQL, historical manifests, accepted source hashes, grants or provenance pins**. The fixture's owner connection plus SET ROLE is test machinery, never an approved deployable credential path.

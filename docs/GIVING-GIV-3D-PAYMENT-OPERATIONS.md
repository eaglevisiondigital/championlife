# GIV-3D payment operations — BUILD foundation

Provider-neutral sibling `codex/giv-3d-payment-operations` starts at accepted GIV-3A `1410ebc824cdf0b9721c95db0cb41229b74a0274`. Neither NMI GIV-3B nor Authorize.Net GIV-3C files are ported or changed. Their accepted heads remain `1ea6971c2a0273b1a15c132d7793b12c2822901e` and `48c83592d43d469539d44f36f6d9cfaa9ff7325a`. NMI hosted acceptance remains paused only for sandbox credentials. This build does not supersede either adapter and never connects to a provider.

## Canonical model

The accepted Giving session, lines, immutable route snapshots, transaction legs, ledger, logical methods/private gateway profiles, recurring instruction, canonical refund/void request, receipts, journals and idempotency store remain authoritative. Additive local migration `20261015142024_giving_payment_operations_giv_3d.sql` adds private operational issues, safe observations, approval metadata, recurring controls/future change requests, method defaults, incidents, resolutions/notes, held event intents and work leases. It adds no second financial ledger, checkout, processor integration or donor identity model. All new relations have RLS and deny raw access including service callers. Narrow invoker public wrappers delegate to guarded definer functions with empty search paths and explicit grants.

The issue projection derives canonical failed/disputed/partial sessions, method expiration, pending adjustments, recurring failures and missing/disabled gateway configuration. A trusted service can append bounded normalized observations for unknown results, provider lookup and settlement/dispute questions. No service observation promotes a financial leg, posts the ledger, reconciles money or generates an issued receipt. Counts never use fake application values. Each issue keeps one typed fingerprint, priority, assignment, revision, next action and links to original canonical records. Resolutions preserve exceptions and append reason/operator/time. Internal finance notes never enter donor projections.

## Permissions and approval

Current `payments.view` protects detailed queues. Operations have separate `payments.manage`, `payments.refund.request/approve/execute`, `payments.void.request/approve/execute`, `payments.recurring.manage`, `payments.method.manage`, `payments.reconcile` and `payments.issue.assign` checks; export additionally requires `finance.export`. No grants are seeded. Reports-only leadership can request count summaries with `finance.reports.read`, without donor/method/configuration/adjustment access. Authorization and owner are rechecked under the accepted organization financial lock before any mutation or idempotent replay. The browser clears late results, forms and confirmation dialogs on sign-out/current-permission changes and rechecks on focus, workspace refresh and a 15-second visible-page interval. Hosted revocation is not claimed.

Refund/void workflows extend `giving_refunds`, freezing original account/route snapshot in approval metadata. Exact full/partial amounts reserve only remaining canonical principal. Default approval is required and self-approval is denied. Policy can explicitly configure threshold, currency, approval requirement and self-approval; there is no hardcoded dollar threshold or new finance-manager role. Approval snapshots preserve the policy at request time. Requested, approved, rejected, execution_pending, processing, completed, failed and review are modeled alongside legacy recorded status. Rejected reservations release principal without deleting history; a narrow forward update to the existing refund reservation calculation excludes rejected requests. The original GIV-1 migration is unchanged. A second pending void for the same original leg is rejected. Eligibility is rechecked before queuing execution. Even approved execution is held; no runtime or financial finalizer is activated.

## Recovery and recurring

Unknown/timeout, fraud, duplicate suspicion, configuration/routing and closed/invalid/expired method failures cannot automatically retry. An unknown result must be looked up through the original operation/account before a reviewed explicit retry request; not_found/known retryable failure may prepare held work. Claim-time validation rechecks current reconciliation. No automatic retry is the policy default. Configured day offsets create held jobs for reviewed retryable recurring failure categories, never a charge. Maximum attempts/failures move work to review/dead-letter. Safe donor messages omit raw provider codes. The server-only `operations.mjs` consumes normalized provider outputs without NMI/Authorize.Net branches; its injected recovery worker can only perform a separately enabled lookup, and defaults disabled.

Operational recurring state supports active, paused, payment_method_required, past_due, cancel_pending, cancelled, completed and review. Pause holds future Kingdom Propel work while preserving provider mappings; it does **not** claim to pause a pre-existing external ARB/vault schedule. No such external schedule exists in this build. Resume requires a reviewed active/current logical method compatible with every original gateway route. Immediate cancellation preserves history; deferred cancellation must use the donor's existing agreed end date. Future amount/designation requests require exact new lines, an effective date and a reviewed donor-authorization reference; they are append-only **held change requests**, not silent rewrites or claims of externally verified consent. Original lines/transactions remain unchanged. Provider update/cancel/amount application will require separately reviewed execution and verification.

Five-minute job leases are independent of financial posting. Expired lookup leases can return held; expired charge/retry ambiguity moves to review and lookup, never blind recharge. Stale accepted provider operations retain their original lease token/history and move to review with a separate lookup job, so the old claim function cannot reclaim them. Expired/recovered claim replays cannot return a usable stale lease. No lease token is returned to the browser. Work claim is service-only and requires current initiating staff authority where applicable.

## Donor and staff workflows

New shared-shell pages cover Payment Operations, Issue Queue, My Payment Work, Transaction Detail, Session Detail, Recurring Management, Refund Detail, Reconciliation Detail and safe method management. Dropdown choices come from canonical funds/accounts/methods/eligible staff. Filters include type/provider/destination/MID/date/exact amount/assignee/status and safe donor/session/receipt/reference/last4 search. Queues/reports/exports explicitly show at most 500 newest matching issues; refine filters for a bounded export. Full canonical count summaries remain uncapped, and direct issue detail is not restricted to the first page. Current grants control actions; confirmation dialogs label the action and emphasize held execution. Compact Giving Overview/Pastor cards show finance counts only.

`payment-history.html` requires a separately reviewed active financial account link, not email matching or general portal access. It projects owned sessions, completed vs failed/unconfirmed amounts, purpose/fund, receipt references and refund state without gateway/MID/token/customer/internal-note data. One logical method appears once regardless of account-specific profiles. Add/replace are audited held hosted-entry actions with no raw PAN/CVV/bank inputs. Default selection requires a current active method. Removal is barred until an active recurring instruction is safely remapped; the guard also applies through older donor/staff removal paths. Expiry uses the last day of the month, including leap years.

Operational events follow owner/subject/kind/event-key/time/held-delivery structure for Communications Core consumption. There is no new message sender or automatic enqueue. The optional staff task hook records a held intent referencing the issue; a later authorized consumer must use existing canonical follow-up/work APIs and their People/follow-up grants. It does not create a second task system or silently grant care/People access. The service-only refund-completed notice requires an already recorded/completed canonical refund and its immutable financial outcome. It emits a held intent only; approval alone cannot fabricate completion. Disputes have a safe queue/category/due-date foundation; a full evidence portal remains out of scope.

Genuine races cover issue claim by different staff, duplicate approval, duplicate refund request, duplicate retry, reconciliation resolution and recurring retry lease. Browser checks use disconnected synthetic fixtures excluded from the public artifact; no actual provider or remote database participates. Responsive/accessibility/console proof is BUILD-only.

# Campaign assignment governance — unverified review binding only

This additive source package starts at PR82 `d36afcffbcbce97307350841e59738cc49924d20`. It reuses PR81 `prepareAssignmentReview`; it does not change the PR80 backend, PR81 adapter, PR82 directory/mount or frozen PR61. No issuer implementation, SQL, authority registry, source-map writer, permission installation or UI mount is provided.

## Implemented offline behavior

`tools/outreach/assignment-governance-review.mjs` adds two pure review-document functions:

- `prepareAssignmentGovernanceReview(packet)` binds the existing canonical request hash to proposed issuer/reviewer/worker evidence, proposed policy parameters, source-provenance/steward references and audit/revocation design references. It requires exact JSON shapes and rejects getters, prototype overrides, unknown fields and malformed values before reading nested input. Identity references must agree with the existing request. Proposed human-binding references must be different even when account UUIDs differ.
- `inspectAssignmentGovernanceReview({original,current,review,observedAt})` recomputes both bindings and identifies stale source, identity, authority, scope, policy, revision or evidence changes. It reports revoked/expired/future reviews, reviewer mismatch, retroactive assignment and intervals exceeding the supplied *proposed* limits. A changed request must be reviewed again; it is never redirected to new evidence. The observation time is explicit, not an implicit workstation clock.

Every result has `executable=false`, `authority=unverified`, `policyStatus=unapproved`. A structurally consistent comparison is labeled **unverified-consistent**, not authorized, approved or ready for execution. Other comparisons are **review-needed**. Invalid structure throws a field-only error. Contact, export and messaging remain false.

All inputs, hashes, actor IDs and observation times remain **caller-supplied assertions**. Different hashes cannot prove different actual humans, authority, a current session, an approved policy or unchanged database state. A caller can fabricate a fully consistent packet; tests explicitly demonstrate that it still cannot authorize anything. Reusing the same stale hashes cannot reveal a real authority revocation or replacement that the caller omitted. There is no trusted attestation verifier, persistent reviewer approval, replay store, authoritative revocation lookup or permission mutation behind these functions. Do not mount them as an authorization endpoint.

The packet carries `max_assignment_seconds` and `max_review_seconds` solely to compare a review with its stated proposal. Neither field has a default. The only numeric ceiling is the technical safe integer range used by the format; it is **not a permissible operational grant duration**. The suggested **90-day assignment** and **24-hour review** intervals remain owner proposals, not approved policy, and do not appear as executable defaults. Test intervals are fictional arithmetic fixtures. The retention reference records a proposed policy document hash, not an approved retention period.

The original canonical request binds organization, campaign, exact `public.outreach_registrations` record and source, observed campaign/record revisions, source-map and record snapshots, worker identity, capabilities, finite dates and reason. The supplement cannot broaden those fields. It adds distinct-human evidence references and separate reviewer authority, steward/mapping-writer policy, retention and revocation references that the original request does not carry. Requester is proposed issuer; a separate actual submitter would require an explicitly reviewed contract extension, not silent substitution.

After those decisions and separate implementation authorization, the smallest future issuer should be one narrowly scoped server transaction over the accepted campaign assignment and record-followup model, with independently reviewed registry/audit dependencies. It must not install historical broad grants or infer authority from People administration, event registration, Partner affiliation, role labels, `service_role` possession or a client-supplied approval.

Before writing, acquire a shared and consistently ordered serialization boundary used by **every** authority change, approval, mapping replacement, identity correction, assignment change and revocation path. Lock current actor authority/session/effective-date records, exact campaign/source/registration, reviewer approval and target assignment; protect absence with a locked parent or equivalent reviewed uniqueness strategy. Verify current issuer/reviewer/worker identity and human independence, authoritative review UUID/hash/revision, source/identity snapshots and policy version **after the required locks**, using server time. Revalidate finite deadlines after waits and immediately before commit. A free-standing second check without compatible revocation locks is insufficient. Exact lock order must be proven against the actual future schema; this document does not claim that a new registry already exists.

Reassignment, extension, reduction and renewal require their exact observed positive target revision, not a nullable upsert. Creation must prove absence and may not overwrite an existing record. Request-ID replay is idempotent only for the exact stored canonical bytes and committed result; reuse with different scope/evidence is a conflict. A stale approval can never authorize a replaced case/mapping or changed identity. Concurrent review/revocation must produce one coherent transaction ordering; failures and audit-write failures roll back all permissions and successful-change audit effects. Denied attempts may have a separate accurately labeled security event, never a successful issuance event.

Immediate revocation requires an approved authoritative withdrawal path independent of an ordinary two-person issuance delay. The owner must decide who can revoke in an emergency and how independent review/audit follows; this proposal does **not** invent that authority or let expired review extend it. The comparator's timing checks also apply to a `reason=revoke` review document, but its `review-needed` result must never gate an independently authorized emergency containment action or require a future-effective date before withdrawal. Completed revocation must prevent subsequent reads/writes at the database boundary. Already submitted transactions must serialize consistently; UI cleanup alone is not revocation. PR81/82 stale-response retirement and denial cleanup remain defense in depth. A persistent registry must record irreversible review withdrawal and expiry; the offline `status=revoked` flag is only a negative test observation.

Successful issuance must atomically write an immutable audit with the committed effect and exact revisions; no contact details, prayer, lesson answers, financial values, raw documents or secrets belong in its public/private review metadata. Preserve original immutable history, separate grant expiry from audit retention, and use an owner-approved minimum metadata and evidence retention/access/correction process. Do not delete evidence automatically when an assignment expires. Restrict audit reads to approved reviewers/operators and preserve separate immutable correction/revocation events.

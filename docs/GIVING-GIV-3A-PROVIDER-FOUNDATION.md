# GIV-3A — secure provider foundation build

Status: BUILD candidate, stopped at build review. Based on Chat-accepted GIV-2C `edf82fb34e8db448a0d6c6465a3799c75993d5a2`, on `codex/giv-3a-provider-foundation`. GIV-1/2A/2B/2C remain accepted prerequisites; no prerequisite is merged by this package.

## Implemented scope

The existing Giving Core remains the only financial system. This package extends canonical gateway accounts, processor routes, sessions, session lines, transaction legs, recurring instructions, private payment profiles, refund requests and audit. It does not create a second payment ledger. Additive local migration: `20261014171912_giving_provider_foundation_giv_3a.sql`.

The permanent ownership chain is organization → fund/payment purpose → merchant destination → gateway account → processor/MID route → transaction leg. Fund hierarchy stays independent from merchant routing. One NMI gateway can represent multiple explicit routes; separate Authorize.Net accounts can have separate customer/payment profiles. External processor identifiers are opaque metadata, not claimed boarding support. Champion Life and SowGo remain separate financial owners; front-end brand does not authorize or transfer financial ownership.

Provider-neutral operations cover tokenization, customer/method attachment, authorization, capture, sale, refund, void, recurring create/update/cancel, transaction/settlement retrieval, webhook verification and normalized error handling. `nmi`, `authorize_net`, `manual` and `future` are the native codes. Legacy GIV-1 placeholder codes remain readable for compatibility; no Stripe dependency is introduced. The adapter contract contains no provider URL, SDK or network transport. Every real operation is held; no verification method returns a successful real-provider signature.

## Canonical checkout and classifications

The staff preparation boundary creates one exact, bounded Giving session with immutable routing snapshots and independently routed legs. Money is PostgreSQL bigint and JavaScript decimal strings/BigInt, never floating-point arithmetic. A four-line $385 checkout supports $200 Main, $50 Youth, $100 Outreach and $35 merchandise across four MIDs. Lines sharing the same owner/destination/account/MID consolidate unless the route explicitly disallows consolidation. Cross-owner, currency/environment mismatch, ambiguous route keys, stale configuration revisions and changed idempotency content are rejected.

Supported purposes: charitable_contribution, event_fee, registration_fee, merchandise, deposit, camp_fee and other_payment. Non-contributions cannot carry tax eligibility. Contributions require a canonical fund. Event/Form/campaign attribution uses existing canonical references; merchandise/inventory management remains a later module. Published Form classification cannot be overwritten by checkout input. Accepted pre-GIV-3A Form lines are not rewritten: their purpose is projected from the exact original immutable submission version, so later Form publication cannot turn an old event fee into a contribution. Legacy storage may have a null additive purpose annotation; the effective projection is explicit, while every new native/Form line is explicitly classified. Form detail opens the submission's existing Giving session and requires both current payment view and Form submission access. No parallel session/ledger is fabricated. Public guest Forms remain payment-held.

The UI exposes line designations, exact total, individual legs, a preview of recurring/anonymous/email choices, a disabled payment element, and the exact message “Payment processing is not yet enabled.” No card/bank input exists. Anonymous choice is disabled where no contribution is present. Receipt preview includes canonical date/reference/total, classifications and an honest unselected method summary. No receipt is issued/sent and authorization is not treated as settled giving. Provider-neutral outcome summaries distinguish all_success, partial_success, all_failed and pending_review; unknown outcomes require review without blind retry or automatic compensation.

## Methods, secrets and execution

Logical donor methods hold masked brand/last4/optional expiry/billing metadata. One logical method can map to several gateway-specific private profiles and explicit compatible routes. Customer IDs are scoped by owner/person/gateway/environment. Synthetic attachment is service-only, sandbox-only and accepts only `synth:` references; changed descriptors/scopes on retry are rejected. Removing a logical method disables its private profile references. Donor reads/removal require a separately reviewed active financial account link, never an inferred email/portal match. Browser/staff projections do not expose provider tokens, customer refs, credential bindings or full MID references.

Credentials belong only in secure runtime secret storage. Private database metadata stores an owner/account/environment/version reference, with exact scope validation. The runtime resolver verifies every scope component before resolving a runtime key and status projections never return a secret. This build configures no secret binding or real credential. Raw PAN/CVV/bank/password/key/response fields are not accepted by the provider contract or checkout payload; sensitive provider errors are mapped to fixed safe messages.

Execution requires explicit global, organization, gateway, MID route and checkout/Form switches, exact environment/route/amount/token binding, current initiating authority, verified capability, credential binding and a current session. A separate GIV-3A stage gate is always false, with database constraints holding global/org/route/form switches false and gateway defaults false. Even forged all-true runtime gate data is forced held by the worker. The existing trusted finalizer cannot post native_checkout or platform_form sessions. A later reviewed migration/adapter is required to activate execution; possession of a credential or ordinary finance access cannot do so.

Seven distinct keys: payments.view, payments.configure, payments.route, payments.refund, payments.void, payments.recurring.manage and payments.provider.activate. No real grants are created. A separate initially empty, expiring elevated platform-authority registry accompanies activation attempts. Attempts are audited and return held regardless of the caller's keys. Reports-only leadership cannot configure or activate providers. Navigation is permission-filtered; backend RPCs still recheck authority and tenant after the financial lock. Revocation/sign-out clears protected data and rejects late reads.

## Journal and lifecycle foundations

Safe operation metadata binds idempotency, original canonical leg/amount, optional original refund/void request and a payload digest. One operation lease is created; immutable journal records retain held/claimed safe status. Request replay with changed content is rejected. Unknown outcomes do not automatically retry. Authorization/capture/sale are separate contract operations; no real execution occurs.

Full/partial refund and void preparation reuse canonical Giving requests/refunds, distinct permissions and original-leg audit. Void validity follows accepted Giving lifecycle rules. Recurring weekly/biweekly/monthly/annual frequencies extend the existing canonical instruction, whose multiple fund lines can map to multiple routes. Provider schedule references are implementation details; a canonical instruction/due time produces one held job and no subscription/charge.

The undeployed webhook endpoint rejects POST with 503 while no verifier is configured, before parsing/logging/persisting unauthenticated payloads; non-POST is 405. The provider-neutral raw-body hook is bounded. Service-only synthetic normalization requires verified instrumentation and exact sandbox account/route/leg, dedupes provider event IDs, detects changed replay and creates a held reconciliation event. Dispute status is a hook, not a dispute portal. Synthetic events never promote payment status or post a ledger entry.

Settlement metadata represents account/MID, batch, date, currency, gross, nullable fees/net and count. Missing fee/net stays NULL; known net must reconcile. Replay content is digest-bound. All new tables use RLS with revoked raw access, including service callers; narrow guarded RPCs own writes. Immutable token scope, checkout context, journal, webhook, settlement and recurring records preserve history.

Local fixtures/clusters are disposable and cleaned up. The deterministic test provider lives only in backend tests, has zero network calls and is excluded from public/server production artifacts.

Raw private evidence/screenshots remain outside this repository. This is build evidence, not hosted processor acceptance.

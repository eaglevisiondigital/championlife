# P1 durable notification delivery — implemented, disabled candidate

November 18 Issue159 authorizes source implementation and isolated tests, not production writes, credentials, message approval, staff grants, hosted deployment or paid resources. The nine proposed messages in OUTREACH-TEAM-NOTIFICATIONS.md remain unchanged and unapproved. This implementation never imports or automatically approves them. P0 application receipt SQL, payloads, keys and worker are unchanged.

## Installed state and authority boundaries

The separate forward candidate creates ten private RLS tables: runtime controls, explicit event operators, immutable policy versions, deduplicated intents, immutable attempts/events, signed-channel receipt evidence, immutable receipt bindings/conflicts and P1-only suppression. No browser or service role has direct table privileges. Public notice_workspace is authenticated and checks current event staff access plus a separate explicit operator capability; staff.manage alone grants no notice authority. Worker RPC is service-role-only. All functions use an empty search path.

Installation inserts only one runtime row: sending and lookup false, environment/account unset. It inserts no operator, approved policy, recipient, staff grant or message. No schedule or database trigger produces messages from Team/P0 changes. Preparing a held intent is an explicit authorized action on an actual current P1 history event. Its logical history/member/kind key and provider key are durable and immutable; replay, another policy version or deleting evidence cannot manufacture a fresh send. Historical approvals after status cycling are refused. Reassignment creates distinct authoritative assignment history; companions are never parsed into recipients.

An approved policy version must separately bind exact copy digest, event/kind, approved actor/reference/time, environment/account, sender/reply-to, effective/expiry window and supported recipient, consent, retry and retention contracts. Policy versions cannot be edited; revocation is permitted. There is no public approval or activation API. An explicit per-intent review binds the recipient and consent evidence before freezing the exact provider JSON and SHA256. Missing approval or consent, SQL NULL, invalidated state and unsupported rules fail closed.

The currently implemented recipient capability is verified adult own-account email with one active canonical portal link and an unambiguous canonical email. It is not an approved product policy: no real policy selects it. Minors, guardian routing, shared/ambiguous contacts, applicant-email fallback and unverified identities remain held until separately approved and supported. Supported retry is no automatic retry after a committed start. Supported retention is evidence retained pending manual review, with no automatic purge/deletion; a different retention/purge contract needs separate implementation/review. These technical ceilings do not silently approve recipient or retention business rules.

## Claim, start and uncertain outcomes

Claims are event-scoped, short database transactions using the campaign lock and SKIP LOCKED intent selection; no database lock spans networking. A thirty-second lease uses a random CAS token. An expired lease with no committed attempt may be reclaimed; a stale token cannot start or overwrite another lease. Before start the server rechecks current operators, staff directory/grants/dates, policy, canonical recipient/link/consent/suppression and authoritative member/source/guardian/driver/assignment/leg snapshot. Runtime/environment/lookup gates are re-read after lock waits.

Start commits one immutable attempt before any POST. The worker verifies the exact frozen JSON bytes/digest and original outreach-team-v1/<intent UUID> key. One invocation performs at most one POST, without an SDK retry loop. A non-success, timeout, malformed result, crash after provider acceptance or failed local result persistence never proves unsent. It remains in-flight until reconciliation HOLD, or enters HOLD immediately. There is no retry/rotate-key/requeue/delete API after start, including after Resend's24-hour deduplication window. An already-started external POST cannot be atomically revoked or recalled.

Successful send response records provider acceptance only. Delivery is separate evidence. A stale result may append its real accepted-provider fact and bind its original attempt, but cannot clear an expired/revoked/reconciliation HOLD. Provider IDs are unique; a result without a committed nonnull attempt and lease is refused with no revision/audit/binding advance.

## Signed evidence and reconciliation

The separate webhook verifies Svix HMAC-SHA256 over the original bytes, message ID and timestamp using WebCrypto verification before JSON interpretation. Size/depth/time bounds, a five-minute signature timestamp tolerance, strict duplicate/prototype-key rejection and an official Svix known-answer vector are tested. Only bounded IDs, types/times and hashes cross into SQL; recipient lists, bodies, raw signatures and secrets are not retained. Open/click tracking never changes participation or attendance.

Receipt IDs dedupe durably within environment/account. Append-only bindings allow a webhook that arrives before result persistence to be adopted atomically once the provider ID is proven. Contradictory signed bytes retain both implicated provider IDs and hashes; each bound intent stays held, including an ID bound later. Receipt/email locks use normalized UUIDs and a consistent order. Negative outcomes remain sticky; later positive/out-of-order evidence cannot erase bounce, complaint, failure or suppression. P1 suppression never edits the P0 receipt outbox or marketing lists.

Unknown provider IDs initially remain unmatched/HOLD. A separate, default-off GET-only reconciliation capability requires a current explicit reconciliation operator's review of one exact provider ID, a distinct provider-read credential, runtime lookup approval and a CAS lookup token. The provider record must prove the frozen from/to/reply-to/subject/text, unique intent tag and attempt timestamp; cc/bcc/scheduling/HTML or missing/unknown last_event refuse. An authenticated GET is not mislabeled as a signed webhook. Redacted provider-lookup evidence is recorded separately, and earlier matching signed receipts are adopted. No resend occurs. If evidence or GET access is unavailable, keep HOLD. Current supported lookup states are sent, delivered, delivery_delayed, failed, bounced, complained and suppressed; unsupported states are not inferred as acceptance.

Reporting requires a current event-specific reporting capability and staff access on every call. It exposes bounded counts and opaque intent IDs, notice/state/hold codes/times, attempt-start presence, signed outcome types, lookup outcome codes and conflict flags. It omits recipient/contact/Person/guardian/provider IDs, payloads, private review notes and raw evidence. No new report UI or public artifact entry is published by this package.

## Runtime and validation limits

Source entry points are separate Supabase worker/webhook functions. A future deployment needs both gateways configured with verify_jwt=false: the worker enforces its own dedicated invocation secret, while the webhook enforces raw Svix verification. Missing mode, environment/account, credentials or DB approvals remains disabled. No secret or gateway setting was created/applied here. Provider-account identity is an approved configuration binding; no real credential/account compatibility is claimed.

Local end-to-end tests use the actual SQL and JavaScript with labelled synthetic Auth/policy/recipient data and a mock provider. They cover concurrent producers/workers/start CAS, stale leases, post-send persistence crash, lookup proof, early and conflicting receipts, revocation/expiry, canonical/source drift, minor refusal, suppression, immutable evidence, redaction and P0 preservation. HTTP tests verify cryptographic and malformed-input boundaries. Prior genuine P1/Auth/CRM/travel acceptance remains preserved; these new tests do not claim genuine Resend delivery, a deployed Deno function or production callback success.

See MINDEN-P1-DEPLOYMENT-PLAN.md for the exact review/rollout/stop package and pending owner decisions. Production sending, lookup, schema and callback configuration remain unapplied.

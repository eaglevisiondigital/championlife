## First implementation slice

Four additive tables separate organization identity, participant affiliation, explicit staff permissions, and organization-specific contact records. Seed organization configuration: Champion Life Church and SowGo. Existing learner profiles and courses remain independent and retain their existing policies.

Permissions are provisioned by trusted server operations only. No browser user can self-assign a permission or affiliation. No real staff member is granted permissions automatically. `people.read` and `people.update` are independent and both are needed for editing. Identity and organization columns cannot be changed by browser clients. `people.export` is a separate future application capability; it cannot prevent someone with read access manually copying information they can already view. There is no export endpoint yet.

The existing St. Lucia claim RPC retains its name/signature. Its privileged implementation moves to the private schema, checks an authenticated non-anonymous user with a verified email, ignores registrations owned by someone else, and serializes same-email claims. Public form inserts cannot specify an account owner; consent must be supplied. Unnecessary TRUNCATE, REFERENCES and TRIGGER grants are removed from the outreach table. Existing St. Lucia form already sends explicit consent and no account ID.

Login redirect allowlisting is prepared on this development branch. Only the discipleship dashboard and existing course paths can be selected; external URLs, script schemes, and login loops fall back to the dashboard.

## Operational follow-up implementation

Follow-up tasks attach to an organization-specific person using a composite foreign key. Separate `followup.read` and `followup.manage` permissions are additive; both require `people.read`. No existing grants are changed and no staff is auto-provisioned. Affiliation alone gives no task access.

Authorized managers create next-step tasks from People, set a due date, leave tasks unassigned or assign themselves, and update open/completed/canceled status. Database validation also permits another explicitly authorized same-organization assignee; the team-assignee picker is deferred until staff management is built. Revocation removes visibility immediately at the next database request. Existing assignments to revoked staff can be cleared or updated but do not confer access.

The new Follow-up view supports status/assignment filters, pagination, contact names, and recent task activity. Updates use a server-maintained revision so stale edits cannot silently overwrite someone else's work. Creation and updates append actor-attributed before/after audit events, inaccessible across organizations and not editable by browser clients. No task deletion is exposed. Operational titles must not contain private care notes; restricted care remains separate. Nothing sends email/SMS or implements the deferred host church process.

Two private trigger functions validate staff identity, scope and assignee eligibility and record history. They have fixed empty search paths and no public/anon/authenticated EXECUTE grants. Normal writes still use table RLS; no service key is used in the browser. Account and organization changes close task dialogs, clear private content and ignore late responses.

Validation: 25 isolated PostgreSQL follow-up checks and synthetic DOM create/update/conflict/history/access checks, plus the existing foundation and lesson suites. jsdom is pinned as a test dependency. Live email and visual browser acceptance remain required before frontend publication. Staff management/provisioning UI, consent-aware outreach-to-CRM linking, people creation/import and real staff assignments remain pending. Do not infer follow-up consent from the existence of a task.

## Staff administration, contact creation and team assignment

The Staff access screen now lists organization staff labels, active permissions and recent access changes. A verified existing account can be added by its exact email; this action does not send mail or create an Auth user. Later edits use the scoped directory user ID and a revision check. Only `staff.manage` holders can administer access, and they may delegate only permissions they currently hold. Browser administration cannot grant `staff.manage`, edit the actor's own access or edit an active administrator. Trusted provisioning is required for those actions. An empty permission set revokes the selected staff member's operational permissions. Dependencies require people.read for people/follow-up operations and followup.read for followup.manage.

A private server function serializes organization access changes, rechecks authority, validates verified target accounts, rejects stale revisions and appends immutable audit events. Public RPC wrappers run as invokers. The private schema must remain excluded from PostgREST. Directory access is RPC-only; assignment callers receive only eligible organization staff IDs/names/revisions, with no email or permission list. Administrators can see scoped permission lists. The directory's RLS is enabled with no direct authenticated table grant.

People now supports Add person for `people.create` plus `people.read`. New contacts remain unlinked (`user_id` is null); matching email does not grant account ownership, imply membership, or establish communication consent. Contact updates have a server-controlled timestamp and audited before/after values. These operational records remain distinct from the learner profile. The new contact-write triggers require verified staff identity and explicit permissions; future server imports must use an explicitly reviewed path rather than assuming service-role writes are unaudited.

The follow-up editor fetches eligible staff from the selected organization's directory. Existing inactive assignments can be cleared without conferring access. Browser dialogs ignore late responses after cancel, organization change or account change; duplicate in-flight submits are disabled. No invitations, email/SMS, contact imports or host-church workflow automation are sent/started.

Validation includes 30 new PostgreSQL access/contact checks and an integrated synthetic UI flow covering delegation, contact creation, team assignment, revocation, revision and account clearing. Existing tests remain release gates. Named initial administrators, actual email login and desktop/mobile visual acceptance are still pending. No real access is assigned by the migration.

## Person record and daily overview

Click a person's name to open a focused record dialog. Contact details are reloaded from the server; tabs provide the last 30 contact audit events and paginated person-specific follow-up. Each query includes organization and person filters, and existing RLS is retained. History deliberately excludes staff-access events. Values render as text, including before/after contact changes. Permissioned edit/create/update actions reuse the established forms, and a saved change refreshes the open person record. Record dialogs and pending responses are cleared on organization/account change.

The Overview now requests exact permitted people counts, the current user's open/overdue task counts, and up to five assigned open tasks ordered by due date. It does not invent counts when a query fails. Overdue uses the device's local calendar date, shown alongside the result. Updating a task from Overview refreshes that view. No new tables, grants, production migrations, messages or deployments are required by this slice.

New synthetic DOM tests cover record/history/task scope, safe text rendering, callbacks, denied task access, late response isolation, count queries and account clearing. Existing database and UI suites remain in place. These tests do not replace real email sign-in or desktop/mobile browser acceptance.

## Household records and relationship management

Households now have a staff workspace with active/archived views, paginated records, creation, renaming, archiving/restoring, contact search, and paginated membership. Adult/child/other relationships can be changed. Removal marks a relationship inactive; restoring retains its identity and audit history. Duplicate household/person pairs are rejected. The person record has a Households tab showing up to 30 recorded relationships.

Separate households.read and households.manage permissions require people.read; management also requires household read. Staff administrators can delegate these permissions only when they hold them. Database RLS and composite organization foreign keys isolate households and contacts. Server revision checks protect both household and membership edits. The membership trigger locks its parent household and requires active status, preventing additions/changes to archived households. No destructive delete operation is exposed.

Household and member changes append to organization_admin_events, with household audit visibility requiring households.read and people.read. Household relationships never create identities, assign account access, establish legal guardianship, authorize child pickup or imply communication consent. A contact may participate in more than one household without account duplication. Family self-service, verified guardian permissions, custody/check-in rules, household giving statements, calendars and the full Family Hub remain separate work.

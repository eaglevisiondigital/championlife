## First implementation slice

Four additive tables separate organization identity, participant affiliation, explicit staff permissions, and organization-specific contact records. Seed organization configuration: Champion Life Church and SowGo. Existing learner profiles and courses remain independent and retain their existing policies.

Permissions are provisioned by trusted server operations only. No browser user can self-assign a permission or affiliation. No real staff member is granted permissions automatically. `people.read` and `people.update` are independent and both are needed for editing. Identity and organization columns cannot be changed by browser clients. `people.export` is a separate future application capability; it cannot prevent someone with read access manually copying information they can already view. There is no export endpoint yet.

The existing St. Lucia claim RPC retains its name/signature. Its privileged implementation moves to the private schema, checks an authenticated non-anonymous user with a verified email, ignores registrations owned by someone else, and serializes same-email claims. Public form inserts cannot specify an account owner; consent must be supplied. Unnecessary TRUNCATE, REFERENCES and TRIGGER grants are removed from the outreach table. Existing St. Lucia form already sends explicit consent and no account ID.

Login redirect allowlisting is prepared on this development branch. Only the discipleship dashboard and existing course paths can be selected; external URLs, script schemes, and login loops fall back to the dashboard.

## Validation

Run `npm ci --prefix tools/backend-tests` then `npm test --prefix tools/backend-tests`.

The PostgreSQL test suite uses PGlite 0.5.8 and synthetic users. It checks organization isolation, dual affiliation, self-promotion denial, restricted updates, immediate revocation, anonymous access, verified-email claiming, repeat claims, ownership conflicts and RLS. The old-schema fixture is deliberately minimal and does not substitute for full production frontend/Auth/SMTP testing. No test creates real users or sends email.

Migrations are incremental against the existing audited schema, not a bootstrap of a blank Supabase project. Do not run `db reset` against production. Both filenames were generated by Supabase CLI. Deploy only the exact reviewed SQL, in order, to the active project. The source migrations are saved before any live application.

## Audit findings still to resolve

1. Shared browser lesson drafts use account-independent localStorage keys and can mix learners on a shared device. Introduce account-scoped drafts, safe guest import, and account-change handling before broader shared-device rollout.
2. Blank answers are filtered out of cloud saves, so clearing an answer does not reliably clear its old cloud value.
3. The worksheet notes field is not included in the current cloud answer payload.
4. Existing course restoration favors non-empty local values without conflict timestamps.
5. Supabase browser CDN dependency is unpinned beyond major version 2.
6. Leaked-password protection is disabled. Current discipleship is passwordless; revisit before password-based staff accounts. Remediation: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
7. Need full SMTP/auth redirect configuration review and an end-to-end sign-in with an approved test identity.
8. Need role provisioning API with auditing, explicit initial staff assignments, people import and full operations dashboard. No sensitive permission is inferred from a tag.
9. Private schema must remain excluded from PostgREST exposed schemas. Its claim implementation independently verifies identity even if called through SQL.
10. Reconcile shared code boundaries with the historical global Propel repository before broader modules.

## Release and recovery

New organization tables do not change existing public routes or learner data. If the new module has a defect, disable its frontend entry points and fix forward; do not drop tables after real data is added. Registration hardening intentionally restricts only unsafe ownership/claim paths. Do not restore the insecure public ownership policy as a routine rollback.

Frontend edits on this branch are not published to main automatically by this task. Live database application and post-deployment checks are recorded in RELEASE-LOG.md once performed.

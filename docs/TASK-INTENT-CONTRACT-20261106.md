# Durable task intent requirements — disposable transaction experiment

Base: PR106 `07e27b055d49313f2f1c292ae96647f70856be20`. Scope is the source-only durable intent investigation in [Issue58 comment6676975263](https://github.com/eaglevisiondigital/championlife/issues/58#issuecomment-6676975263). This package introduces **test-only fixture tables**, not an operational intent registry, task writer, terminal receipt service or migration. The existing canonical task and audit remain the only task system. PR105 bound-write denial is unchanged. RELEASE NO-GO.

## Existing evidence and the missing guarantee

`followup_task_events` records the canonical task, organization, server actor, action, before/after state and time. It contains no task-request intent UUID, accepted request payload or terminal operation state. The separate campaign decision audit's `request_id` belongs to campaign decision operations; it cannot be treated as a canonical task receipt. Existing `task_writer_prepare` captures current identity, exact scope, five revisions and neutral intent but persists no request. `task_writer_reconcile` checks current scope and history and always returns UNKNOWN. This increment preserves both functions and the existing outcome classifier unchanged.

PostgreSQL Read Committed queries exclude other transactions' uncommitted changes; a uniqueness conflict can nevertheless wait for an uncommitted competing insert. A missing row is therefore insufficient to establish either non-admission or absence of pending work. These are documented database properties, not assumptions about a hosted transport. [PostgreSQL17 isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [INSERT/uniqueness](https://www.postgresql.org/docs/17/sql-insert.html).

## Executable experiment

`tools/outreach/task-intent-fixture.sql` is loaded only by `task-intent-contract.native.mjs` through the existing disposable Unix-socket PostgreSQL fixture. Its `task_intent_fixture` schema holds normal PostgreSQL tables so independent connections can observe committed data. They are destroyed with the disposable database. They are not TEMP tables, a production durability mechanism or an approved schema to install elsewhere.

The lab capture helper derives actor/session from the existing server Auth helper and organization/Person from the canonical ordinary task. The requester supplies only a UUID, task, expected ordinary task revision, status and nullable finite date. The helper locks that task first, checks existing ordinary permissions and refuses every campaign-bound task. It then records an immutable full request tuple. A global UUID primary key serializes duplicate proposals, including proposals that locked different ordinary tasks. Exact reuse only reports `EXACT_INTENT_ONLY`; changing any captured task, actor, session, revision or intent field conflicts. Existing capture may be observed after the task revision changes, but this never passes a new CAS or invokes a writer. Global UUID uniqueness and original-session equality are conservative lab constraints, not approved production deduplication or cross-session reconciliation policy.

The helper returns `state=UNKNOWN`, `can_authorize=false`, `can_commit=false`, `automatic_retry=false`, `terminal_verified=false`. It does no canonical task or event DML and creates no receipt. The separate fixture receipt table references an existing task event and permits one receipt per intent and one intent per event. Both fixture tables reject update/delete/truncate. Schema/table/function privileges are revoked from PUBLIC, anon, authenticated and service_role; tables have RLS and no client policies. Tests call them only as the disposable fixture owner. No API wrapper, runtime entry point, signer or credential exists.

The native harness explicitly puts a fictional **ordinary** task update and its fixture receipt in one transaction, using the existing canonical audit trigger. That controlled transaction demonstrates shared visibility and rollback; it does not automatically enforce correspondence or coupling for every possible fixture-owner SQL statement. The suite deliberately inserts a reference to an unrelated old event successfully under the fixture FK, then rolls it back. That positive limitation control proves a stored event reference is insufficient. No fixture receipt is interpreted as terminal authority; the unchanged outcome classifier retains UNKNOWN.

The fixture's independent actor/session/task/event foreign keys do not establish relationships among those records when the owner bypasses the capture helper and directly inserts rows. The helper derives its actor/session correctly, but the fixture schema is not an operational receipt registry. Its append-only triggers constrain normal lab statements, not a database owner's ability to change the schema or disable triggers. Neither fixture-owner access nor a server-stored row proves trustworthy terminal custody.

The experiment establishes:

- A separate observer sees the previous task/history and no claim/receipt while all four changes are still uncommitted. Absence cannot prove no pending operation.
- After a controlled discarded COMMIT response, a different connection can read the lab claim, event and receipt. The harness discards a real successful response as application input; it does **not** cut a socket, reproduce a managed-provider transport failure, restart PostgreSQL or prove crash durability.
- A committed capture without a receipt remains unresolved. Rolled-back admission disappears; a waiting contender can then capture the same UUID. Absence is not an irrevocable rejection tombstone.
- Actual concurrent capture waits are observed, for same-task serialization and different-task uniqueness arbitration. Exact duplicate capture never repeats a task update. Changed payload or task conflicts rather than changing the stored request.
- An actual lock timeout leaves the independent blocker able to commit later. Timeout, elapsed time and missing receipt cannot establish a terminal rejection.
- Explicit rollback, receipt insertion failure and a later PR105 bound-task denial roll back the ordinary control update, canonical event, new intent and receipt together.
- Expired identity and revoked current management deny even exact prior capture access. Bound task/history/binding rows and all pre-existing function definitions remain unchanged.

## Required production contract — not implemented

The following are requirements to resolve in the existing writer architecture before any operational registry or terminal result exists. They are not new permissions, retention policy or authorization to implement a producer.

1. **Authoritative admission and immutable request identity.** A genuinely server-owned committed operation record must bind exact organization, campaign, source/registration, Person/account, task/binding, original authenticated actor/session, all five expected revisions and canonical neutral status/date intent. No email/contact matching, client role, supplied receipt or digest alone proves those facts. Define the deduplication namespace and response to changed payload under the same ID. One task revision is sufficient only for this ordinary lab control; it is not the campaign writer's five-revision contract.
2. **One serialization path for every execution attempt.** All workers and allowed entry points must consult the same immutable intent identity before mutation. Concurrent duplicates must not create a second mutation/event; changed-payload reuse must conflict. Consistent ordering must include task, intent, binding, source, permissions, audit and administrative mutation paths. This experiment covers the named capture races, not the complete lock graph. A matching prior request must never become permission to replay automatically.
3. **Atomic successful receipt.** A committed-success receipt must belong to the exact accepted intent and canonical trigger-produced event in the same successful task transaction. Require the existing five-revision CAS, one task revision increment, exact server actor and before/after event, current source/reviewer/consent authority and a transaction-end fence. A foreign key, hash, matching status or historical event is not that guarantee. The sibling writer investigation owns exact mutation/event correspondence and final-fence proof; this lab does not supply or replace it.
4. **Terminal rejection and no pending execution.** A rollback erases records written in that transaction; it cannot itself leave a durable rejection receipt. A future authoritative rejection procedure must durably settle the admitted operation while excluding all pending and later execution of that same operation through every allowed entry point. How that admission/settlement exclusion works must be independently reviewed before claiming `NOT_COMMITTED` or `NO_PENDING`. A missing event, missing operation row, cancel request, expired session, timeout or elapsed interval does not suffice. No such rejection record or exclusion protocol is implemented here.
5. **Independent current reconciliation.** Read exact committed intent/receipt state through the approved authoritative path under current read authorization. Caller-provided status, cached response or a previously captured favorable head cannot substitute. Historical actor/session attribution and current access are separate checks; safe retrieval following session change must be explicitly designed, not inferred from this lab's strict same-session capture. Unavailable, stale, malformed, conflicting or ambiguous evidence stays UNKNOWN with no automatic retry. A genuine provider's authoritative completion/no-pending guarantees are separate from local SQL visibility.
6. **Retention, revocation and custody.** Retain the immutable admission/result and necessary canonical audit association under an approved finite schedule; expiration/deletion must not silently permit the same operation ID to execute again. Define namespace retirement, evidence expiry, access, withdrawal and retained rejection/commit information before deletion or reuse. Independently current source/reviewer/designation/head custody remains required. The existing owner decision package covers the missing actual people, methods and finite validity/retention; this experiment does not appoint anyone, accept a source or invent a retention duration.

A successful future receipt, once those guarantees actually exist, could establish the outcome of its exact committed operation. It would still confer no new task, contact, finance, export or identity authority. Until then, every actual task outcome exposed by these contracts remains UNKNOWN or the earlier non-authorizing HELD preparation; no automatic retries are available.

## Verification and boundaries

Run `npm ci --offline --ignore-scripts --prefix tools/backend-tests` with cached dependencies, then `node tools/outreach/task-intent-contract.native.mjs`. Native assertions and observed independent connection waits prove the stated lab cases. The experiment creates and changes only disposable fictional fixture records and ordinary control tasks. It never enables a bound mutation, alters existing functions/migrations, publishes a public file, grants real staff, installs hosted SQL, registers keys, contacts people or deploys. Genuine Auth/RLS, provider/transport/crash behavior, real provenance, exact-target recovery/cleanup and separate release authority remain unverified gates.
